# Fix Index Renames and Concurrent Startups in CreateOneOrUpdateAsync

## Rationale

[Issue #247](https://github.com/chA0s-Chris/Chaos.Mongo/issues/247) reports that `MongoIndexManagerExtensions.CreateOneOrUpdateAsync` (`src/Chaos.Mongo/MongoIndexManagerExtensions.cs:32-41` and `:67-76`) resolves an `IndexOptionsConflict`/`IndexKeySpecsConflict` by reading the index name to drop from the failed `createIndexes` command (`e.Command["indexes"][0]["name"]`). That is the name of the **new** model being created, not the name of the index actually causing the conflict. When a caller renames an index while keeping the same key specification, the server reports the conflict against the old index, but the code tries to drop the new name, which does not exist, so `DropOneAsync` throws `IndexNotFound` and the rename never completes.

The same code path is reached from multiple unlocked `IMongoConfigurator` implementations (`OutboxConfigurator`, `MongoEventStoreConfigurator`, `MongoQueueSubscription.EnsureIndexesAsync`, `AnchorStore`) that run during application startup. Unlike migrations, these configurators take no distributed lock, so two application instances starting at once can both observe the same conflict and both try to drop and recreate the same index, racing each other.

This change makes `CreateOneOrUpdateAsync` find the actually-conflicting index by its key specification via `listIndexes` instead of trusting the command echo, and makes the drop-and-recreate sequence tolerate a concurrent caller having already finished the same change.

## Acceptance Criteria

- [x] Renaming an index that keeps the same key specification (triggering `IndexOptionsConflict` against the old name) drops the old index and creates the new one; the old name no longer exists and the new name exists with the expected keys and options.
- [x] An index kept under the same name but given a different key specification or different options (the existing `CreateOneOrUpdateAsync_WhenIndexExistsWithDifferentKeySpecs_ShouldDropAndRecreate` / `..._WhenIndexExistsWithDifferentOptions_ShouldDropAndRecreate` tests and their session equivalents) continues to be replaced; this existing behavior is preserved, not regressed, by the new lookup.
- [x] When another index with the same key specification but a different name and different options already exists (for example, a unique index coexisting with the non-unique index being renamed), that unrelated index is left untouched while the rename still succeeds.
- [x] A conflict whose underlying index cannot be unambiguously identified (no name match, no single index matching the desired definition, and not resolved by observing a concurrent caller's result) still rethrows the original `MongoCommandException`, matching today's fallback behavior.
- [x] When two concurrent calls race to resolve the same rename (including the case where one caller lists indexes after another has already dropped the old index but before it has recreated the new one), both calls complete successfully and the collection ends up with exactly one index matching the desired key specification and options.
- [x] The session overload (`CreateOneOrUpdateAsync(session, model, options, cancellationToken)`) behaves the same as the non-session overload for all of the above.
- [x] `docs/index-management.md` documents that a conflict is resolved by locating and dropping the existing index with the same key specification (not necessarily the same name), that an unrelated index sharing the same key specification is preserved, and that concurrent callers resolving the same conflict is tolerated.
- [x] `dotnet build -c Release Chaos.Mongo.slnx` produces no warnings, and the complete existing and new test suite (including integration tests, via `bash ./build.sh Test`) passes while maintaining the repository's required merged line coverage.

## Technical Details

### Finding the real conflicting index

`IMongoIndexManager<TDocument>` exposes `DocumentSerializer` and `Settings` (giving `Settings.SerializerRegistry`), so the model's key specification can be rendered the same way `MongoEventStore.RenderFilter` (`src/Chaos.Mongo.EventStore/MongoEventStore.cs:131-138`) renders a filter:

```csharp
var renderedKeys = model.Keys.Render(new RenderArgs<TDocument>(indexManager.DocumentSerializer, indexManager.Settings.SerializerRegistry));
```

The model's **requested name** is the name the driver actually sent in the failed `createIndexes` command, `e.Command["indexes"][0]["name"]`: this equals `model.Options.Name` when the caller set it explicitly, and the driver's own computed default name (e.g. `Name_1`) otherwise. Reading it from the command rather than from `model.Options.Name` directly means a default-named index (where `Options.Name` is `null`) is identified correctly, without reimplementing the driver's default-naming convention. Today's bug is not this name itself, but trusting it as the *drop target*; here it is only one input into the lookup below, which still determines the actual index to drop by listing and matching, never by assuming this name identifies an existing index.

Two different normalized option sets are needed, both built from the same rendered keys and the same normalization rule — an omitted/null value on either side (an unset `CreateIndexOptions.Unique`/`Sparse`/`ExpireAfter`/`PartialFilterExpression`, or a `listIndexes` result document that omits the corresponding key entirely) compares equal to the server's documented default (`false` for `Unique`/`Sparse`, no expiry, no partial filter) — rendered through the same `RenderArgs` as the keys (seen in use for real indexes in `OutboxConfigurator.cs:46-50,57-66,70-79`). The rendered keys are normalized the same way on both sides for a text index: the server stores its key specification as `{_fts: "text", _ftsx: 1}` with the indexed field names moved into a separate `weights` document, instead of the caller-facing `{field: "text"}`, so both the requested and the existing side are reduced to the actual set of indexed fields before comparison. This normalization replaces the text field(s) **in place**, at the position where the `_fts`/`_ftsx` pair (or the caller-facing `"text"` marker) actually appears among the compound key's other fields, rather than appending the normalized marker at the end: key position is part of the compound index contract (MongoDB requires every text field in a compound key to be consecutive, but a non-text field can be either a prefix or a suffix of that group), so a prefix field (`{other: 1, field: "text"}`) and a suffix field (`{field: "text", other: 1}`) are genuinely different key specifications — reporting the same `IndexKeySpecsConflict` the server itself raises — and must not be normalized into the same, order-blind shape. The per-field weights themselves are also normalized and compared, independently of the key shape: the existing side reads them straight from `listIndexes`' `weights` document (always fully resolved by the server), and the requested side defaults any field the caller did not list in `CreateIndexOptions.Weights` to the server's own default of `1`, so a same-name text index whose weights actually changed is never mistaken for an already-satisfied request.

The same "effective, not literal" treatment extends to the remaining text-, wildcard-, and 2d-specific `CreateIndexOptions` that the server persists and that can distinguish a same-name index from an already-satisfied request: `DefaultLanguage`, `LanguageOverride`, and `TextIndexVersion` for a text index (each defaulting to the server's documented default — `"english"`, `"language"`, and `3`, respectively — for whichever the caller did not set explicitly, read back from `listIndexes`' `default_language`/`language_override`/`textIndexVersion` fields on the existing side), `Bits`, `Min`, `Max` for a legacy 2d index (each defaulting to the server's documented default — `26`, `-180`, and `180`, respectively — read back from `listIndexes`' `bits`/`min`/`max` fields on the existing side), and `Hidden` and `StorageEngine` for any index type (`Hidden` defaulting to the server's documented default of `false`; `StorageEngine` compared as a raw document on both sides, read back from `listIndexes`' `hidden`/`storageEngine` fields on the existing side). These participate only in the **fully satisfies** predicate (effective comparison), the same as `ExpireAfter` and `Weights`, not in identity: only one text or one 2d index can coexist on the same keys in practice, and `Hidden`/`StorageEngine` never distinguish two indexes that otherwise share the same identity, so there is no rename-detection scenario that depends on any of them, but a same-name request whose value for any of them actually changed must still be recognized as a real options change rather than a false "already satisfied" match. `WildcardProjection` is different: MongoDB includes it in a wildcard index's signature, so it is an identity option (compared as a rendered document on both sides, read back from `listIndexes`' `wildcardProjection` field on the existing side). The existing `expireAfterSeconds` is compared as raw seconds, because a legacy TTL index can store `NaN`, which cannot be converted to a `TimeSpan`: it never matches a requested value, so a same-name index is replaced and an unrelated one is left alone.

The desired side's set of text-indexed fields is the union of the fields rendered as `{field: "text"}` in the key specification and the fields named in `CreateIndexOptions.Weights`: MongoDB accepts, and actually indexes, a field declared only through `Weights`, even when it is absent from the caller-facing key document, so truncating the desired side to only the key-document's `"text"`-marked fields would silently drop that field from both the key-shape and weights comparison — and, for a rename, prevent the renamed index from ever being identified as a match for the existing one (whose key shape, read from `listIndexes`, already reflects the complete `weights` field set).

The throwaway collation probe's cleanup (dropping the probe index again) runs on an independent, bounded (30s) cancellation context, never reusing the caller's own token: if the caller's token is canceled after the server has already created the probe (whether observed during the probe's own creation or while reading its resolved collation back via `listIndexes`), reusing that same canceled token for the cleanup drop would make it an immediate no-op and leave the throwaway index behind indefinitely. The cleanup is best-effort (its own failures, including this bounded context's own timeout, are swallowed) and never replaces or masks the primary exception that is already propagating.

`Collation` is compared by its true effective document on both sides, not by only the fields the caller happened to set. An omitted `Collation`, or one whose `Locale` is `"simple"`, still normalizes to the absence of a collation (matching how `listIndexes` omits the field for an effectively simple index) — `simple` is the one collation value that is never subject to locale-specific tailoring. Any other collation — entirely omitted (inheriting the collection's own default collation) or explicit but only partially specified (leaving fields for MongoDB to fill in from locale-specific defaults, for example `Backwards` defaulting to `true`, not `false`, for some locales) — cannot be resolved locally, so it is resolved against the server instead of guessed or wildcard-matched: `CreateOneOrUpdateAsync` creates a throwaway index with exactly that `Collation` on a freshly generated GUID field name that cannot collide with any real index, reads back the collation document the server actually resolved and stored for it via `listIndexes`, and drops the throwaway index again. This only runs once a real `IndexOptionsConflict`/`IndexKeySpecsConflict` has already been caught (never on the ordinary no-conflict path), and even then only when the literal value cannot be trusted: for an explicit non-simple `Collation`, always (any sub-field could be locale-defaulted); for an omitted `Collation`, when some existing index sharing the same key specification already stores a non-null collation (the collection's own default can then change which existing index is the real match), or when the unresolved definition would fully satisfy the request despite the reported conflict (the omitted `Collation` may inherit a non-simple collection default that differs from a same-name explicitly simple index, which `listIndexes` reports without any collation) — so a rename or an ordinary option change on a collection without any custom default collation never pays for the extra round trip. The probe is created with the caller's `CreateOneIndexOptions`, so `CommitQuorum` and `MaxTime` apply to it as well. The probe is sparse so it indexes no existing documents; a time-series collection rejects a sparse index on a measurement field with `InvalidOptions` and rejects a partial filter combined with a collation, so that rejection is retried once without `Sparse`, accepting a build across the whole collection. Comparing fully resolved documents on both sides also means an omitted or partial `Collation` is never treated as a wildcard that matches anything: two same-key, same-locale indexes that differ only in a locale-defaulted sub-field (e.g. `Strength`) are correctly told apart, and resetting an explicit non-default field by omitting it is correctly recognized as an actual options change rather than a false "already satisfied" match.

### Known limitation: collation resolution needs a spare index slot (human-approved, Option 2)

Resolving a collation through the throwaway probe described above needs one spare index slot in the target collection, because the probe is itself a real index, created before the old index is dropped. At MongoDB's 64-index collection limit, the probe's own `CreateOneAsync` fails with `CannotCreateIndex`, so a rename that would otherwise leave the final index count unchanged (drop one, create one) cannot complete.

This was raised as CR-CX-08 during code review. Two fixes were possible: (1) broaden `CreateOneOrUpdateAsync`'s signature (for example to accept an `IMongoCollection<TDocument>` instead of `IMongoIndexManager<TDocument>`) so the probe can run against a dedicated scratch collection instead of the target, or (2) keep the approved signature and accept the capacity limitation as a documented edge case. The human decision recorded against this issue selected **Option 2**: the signature stays `IMongoIndexManager<TDocument>`, and `BuildDesiredDefinitionAsync` catches the probe's `CannotCreateIndex` failure and rethrows the original conflict exception instead of letting the probe's own, confusing exception propagate — the caller sees the same `IndexOptionsConflict`/`IndexKeySpecsConflict` it would have seen without any collation resolution attempt, not an error about an internal throwaway index it never asked for. Nothing is dropped or created when this happens; the collection is left exactly as it was before the call.

This narrows the acceptance criterion "a test renames an index with the same keys, and the old one is replaced" to exclude the case where the target collection is already at the 64-index limit and the rename requires collation resolution; `docs/index-management.md`'s collation section discloses this caveat.

### Known gap: pre-8.0 MongoDB does not report a Hidden-only conflict (human-approved, Option 1)

CI's `MinimumSupported` job (mongo:7.0.45) failed the two `..._WhenSameNameIndexHiddenChanges_...` regression tests on the published head: reproduced directly against real `mongo:7.0.45` and `mongo:8.0.34` containers, a `createIndexes` request that differs from an existing same-name index only in `Hidden` succeeds silently on 7.0 (no `IndexOptionsConflict`, index left unchanged) but throws normally on 8.0+/9.x, exactly like every other option difference. `CreateOneOrUpdateAsync`'s whole resolution strategy is driven by that exception, so it cannot see this case on 7.0 at all; `expireAfterSeconds`, `sparse`, `unique`, and `storageEngine` were separately confirmed to still throw correctly on 7.0.45, so the quirk is isolated to `Hidden`.

Two fixes were possible: (1) add a targeted post-success check specifically for `Hidden` — after a successful create, when the model explicitly requests `Hidden` and the created index already existed under that name, read it back and compare; a mismatch is treated like a caught conflict (drop and recreate), closing the gap on every server version at the cost of one extra `listIndexes` round-trip on calls that set `Hidden` on an already-existing same name; or (2) document the gap as a known limitation (matching the CR-CX-08 precedent) and branch the two regression tests' assertions by server version instead of a universal update, keeping the exception-driven design exactly as approved but leaving a real, permanent behavior gap on `MinimumSupported` and weakening the tests' pass/fail contract. The human decision recorded against this issue selected **Option 1**: `CreateOneOrUpdateAsync` (both overloads) now reads the created index back and compares its actual `Hidden` value whenever the model sets `Hidden` explicitly, treating a mismatch exactly like a caught conflict. `docs/index-management.md`'s `Hidden`/`StorageEngine` section documents this. This keeps the issue's "full test suite passes" acceptance criterion satisfied, and `CreateOneOrUpdateAsync`'s contract true, on every server version the project supports, without narrowing either regression test by server version.

- **Identity options**: `Unique`, `Sparse`, `PartialFilterExpression`, `Collation`, `WildcardProjection`. These are exactly the options MongoDB treats as distinguishing two indexes that otherwise share the same key specification — it explicitly permits a unique and a non-unique index, a sparse and a non-sparse index, or indexes with different collations, to coexist on the same keys (see the [duplicate key pattern documentation](https://www.mongodb.com/docs/manual/core/index-unique/#basic-and-unique-indexes-with-duplicate-key-patterns) and [sparse/non-sparse coexistence](https://www.mongodb.com/docs/manual/core/index-unique/#sparse-and-non-sparse-unique-indexes)). Two indexes with the same keys and the same identity options cannot coexist under different names: the server raises `IndexOptionsConflict`/`IndexKeySpecsConflict` against the one that already exists, regardless of whether `ExpireAfter` also matches. The **identity definition** of an index or the desired model is its rendered keys plus its normalized identity options.
- **Effective options**: the identity options plus `ExpireAfter`. `ExpireAfter` (TTL) is not an identity option — the server does not require it to match before raising a conflict against a same-identity index filed under a different name, so an existing index's current TTL need not equal the desired one for it to be the conflicting index. The **effective definition** of an index or the desired model is its rendered keys plus its normalized effective options.

`BsonDocument` equality is structural, which lets normalized definitions be compared. Define two distinct predicates over an existing index and the desired model, instead of one ambiguous "equivalent" notion that was previously used for both purposes:

- **Fully satisfies the request**: the existing index's name equals the requested name, and its effective definition equals the model's effective definition (including `ExpireAfter`). An index that fully satisfies the request is the desired end state already in place — including its TTL — and is never a drop candidate.
- **Matches the desired definition** (name-independent): the existing index's identity definition equals the model's identity definition, regardless of its name and regardless of whether `ExpireAfter` also matches. This identifies the index that is, in every way the server treats as identity-distinguishing, the index the caller is trying to create — just filed under a different name, and possibly with a different TTL that the drop-and-recreate below corrects. A bare key match cannot by itself identify the index the server is actually complaining about, because MongoDB permits more than one index with the same keys but different identity options to coexist (for example a unique and a non-unique index on the same field) — only an identity-definition match can, which is also why the server raises this conflict exactly when such a match exists under a different name, independent of `ExpireAfter`.

On `IndexOptionsConflict`/`IndexKeySpecsConflict`, list the existing indexes (`indexManager.ListAsync(cancellationToken)`, or the session overload) and resolve the conflicting index as follows, instead of trusting `e.Command["indexes"][0]["name"]` as the drop target:

0. If any existing index already fully satisfies the request, nothing needs replacing (a concurrent caller got there first); drop nothing and continue with the retried creation below. The listing alone is not proof of success, because `listIndexes` also includes indexes that are still being built, while an identical `createIndexes` waits for that build and reports its failure.
1. Otherwise, if an index with the requested name exists, that is the conflicting index — step 0 already ruled out a full match, so this index's effective definition must differ from the desired model's, in keys or in any effective option including possibly only `ExpireAfter` (this preserves today's existing same-name replacement behavior exercised by `CreateOneOrUpdateAsync_WhenIndexExistsWithDifferentKeySpecs_ShouldDropAndRecreate` / `..._WhenIndexExistsWithDifferentOptions_ShouldDropAndRecreate` and their session equivalents).
2. Otherwise, look for indexes that match the desired identity definition (name-independent, as defined above), ignoring `ExpireAfter`. If exactly one such index exists, that is the conflicting index (this is the rename case: same identity definition, different name, possibly also a different `ExpireAfter` that the recreate corrects — an unrelated same-key index such as a differently-configured unique index does not match the desired identity definition and is correctly left as a non-candidate). If more than one exists, the conflict is ambiguous — do not drop any of them.
3. If no candidate is identified by either step (ambiguous, or none found), do not immediately rethrow; a concurrent caller may be mid-flight (see below) before concluding the conflict is genuinely unidentifiable.

### Tolerating concurrent resolution

Drop the identified candidate through `DropOneIfExistsAsync` (already in this file, `:92-95` and `:129-133`) rather than a raw `DropOneAsync`, so a concurrent caller that already dropped the same index does not fail this call. Then retry `CreateOneAsync`.

Two points in this flow can race with a concurrent caller performing the same resolution, and both must converge on success rather than a spurious throw:

- **No candidate found in step 3 above.** This can mean the conflict is genuinely unidentifiable, or it can mean a concurrent caller already dropped the old index but has not yet recreated the new one, so neither the old nor the new index is present to match against. Before rethrowing, retry `CreateOneAsync`: if it now succeeds (the concurrent caller finished), return its result. If it conflicts again, re-list and check whether an index now exists that fully satisfies the request (as defined above); if so, attempt the creation again so the server confirms the build, for at most three attempts in total. Rethrow the original exception when this recheck fails to observe the desired state, or when the third attempt still conflicts.
- **The retried `CreateOneAsync` after this call's own drop still conflicts** (a concurrent caller recreated the index between this call's drop and create). Re-list and check whether an index now fully satisfies the request: if so, attempt the creation again under the same bound. If none is found, rethrow — a genuine, unresolved conflict remains.

This mirrors the existing idiom in this codebase for tolerating a concurrent actor having already produced the same end state (e.g. `AnchorEvidenceStore.InsertIfAbsentAsync` catching `DuplicateKey` and treating it as success, `src/Chaos.Mongo.EventStore/Integrity/AnchorEvidenceStore.cs:174-183`), applied here to index conflicts instead of write conflicts.

### Shared helper, both overloads

Both `CreateOneOrUpdateAsync` overloads (session and non-session) need the same list-and-match logic, and now also the same throwaway-index-based collation resolution. Add private helpers parameterized on delegates, following the existing `ExecuteDropOneAsync(Func<Task> dropOne)` pattern (`:156-166`): a shared conflict resolver taking a `Func<Task<IAsyncCursor<BsonDocument>>>` lister, a `Func<String, Task>` dropper, a `Func<Task<String>> createOne` bound to the real desired model, and a `Func<CreateIndexModel<TDocument>, Task<String>> createProbe` for the throwaway collation probe, implementing the full-satisfaction-then-name-match-then-definition-match-then-ambiguity rules above, so the session and non-session call sites differ only in which `ListAsync`/`DropOneAsync`/`CreateOneAsync` overload each delegate forwards to.

### Out of scope

`MongoEventStoreConcurrencyIndexSupport.CreateIndexAsync` (`src/Chaos.Mongo.EventStore/MongoEventStoreConcurrencyIndexSupport.cs:78-86`) has the same `e.Command["indexes"][0]["name"]` pattern, but only uses it to build an error message and never drops/replaces the index. It is not part of this issue's scope and is left unchanged.

### Testing

Two internal branches are timing-dependent against a real server and cannot be reliably forced through Testcontainers. Per `tests/AGENTS.md`, cover both directly with a hand-crafted fake `IMongoIndexManager<TDocument>` (solitary tests), since they are otherwise unreachable deterministically:

- The retried `CreateOneAsync` after this call's own drop conflicts again, and a matching index is found by re-listing: the fake returns a conflict from the first `CreateOneAsync`, a `listIndexes` result for the old name, success from `DropOneAsync`, a second conflict from the retried `CreateOneAsync` (simulating a concurrent caller), and a `listIndexes` result now showing the desired index — asserting the call returns that name without throwing.
- The initial lookup finds no identifiable candidate because a concurrent caller has already dropped the old index but not yet recreated the new one: the fake returns a conflict from the first `CreateOneAsync`, a `listIndexes` result containing neither the old nor the new index, and then either a successful `CreateOneAsync` on recheck, or a second conflict followed by a `listIndexes` result now showing the desired index — asserting the call returns successfully in both variants rather than rethrowing.

The collation probe's post-cancellation cleanup is also timing-dependent (it depends on the server having already created the probe index by the exact moment a cancellation is observed) and is covered the same way, with the fake scripted to throw `OperationCanceledException` from the probe's `CreateOneAsync` (simulating the server having succeeded before the client observed the cancellation) and separately from the subsequent `ListAsync` read-back; both assert that `DropOneAsync` is still called for the probe's name with a `CancellationToken` that is not canceled (proving an independent, non-canceled cleanup context is used), and that the original `OperationCanceledException` still propagates.

The pre-8.0 `Hidden`-only silent-acceptance gap (see "Known gap" above) depends on which MongoDB server version is actually running, which Testcontainers cannot force deterministically either; it is covered the same way, with the fake's first `CreateOneAsync` call succeeding (simulating the server's silent acceptance) and the subsequent `ListAsync` read-back returning the existing index with its `Hidden` value unchanged, asserting a drop and a recreate. A second case asserts no drop/recreate when the read-back already matches the requested `Hidden` value (the common case: the server already honored the request), and a third asserts the read-back is skipped entirely (empty `listResults`) when the model does not set `Hidden` at all, confirming the extra round-trip is paid only when a caller actually uses `Hidden`.
