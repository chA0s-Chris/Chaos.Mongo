# Fix Index Renames and Concurrent Startups in CreateOneOrUpdateAsync

## Rationale

[Issue #247](https://github.com/chA0s-Chris/Chaos.Mongo/issues/247) reports that `MongoIndexManagerExtensions.CreateOneOrUpdateAsync` (`src/Chaos.Mongo/MongoIndexManagerExtensions.cs:32-41` and `:67-76`) resolves an `IndexOptionsConflict`/`IndexKeySpecsConflict` by reading the index name to drop from the failed `createIndexes` command (`e.Command["indexes"][0]["name"]`). That is the name of the **new** model being created, not the name of the index actually causing the conflict. When a caller renames an index while keeping the same key specification, the server reports the conflict against the old index, but the code tries to drop the new name, which does not exist, so `DropOneAsync` throws `IndexNotFound` and the rename never completes.

The same code path is reached from multiple unlocked `IMongoConfigurator` implementations (`OutboxConfigurator`, `MongoEventStoreConfigurator`, `MongoQueueSubscription.EnsureIndexesAsync`, `AnchorStore`) that run during application startup. Unlike migrations, these configurators take no distributed lock, so two application instances starting at once can both observe the same conflict and both try to drop and recreate the same index, racing each other.

This change makes `CreateOneOrUpdateAsync` find the actually-conflicting index by its key specification via `listIndexes` instead of trusting the command echo, and makes the drop-and-recreate sequence tolerate a concurrent caller having already finished the same change.

## Acceptance Criteria

- [ ] Renaming an index that keeps the same key specification (triggering `IndexOptionsConflict` against the old name) drops the old index and creates the new one; the old name no longer exists and the new name exists with the expected keys and options.
- [ ] An index kept under the same name but given a different key specification or different options (the existing `CreateOneOrUpdateAsync_WhenIndexExistsWithDifferentKeySpecs_ShouldDropAndRecreate` / `..._WhenIndexExistsWithDifferentOptions_ShouldDropAndRecreate` tests and their session equivalents) continues to be replaced; this existing behavior is preserved, not regressed, by the new lookup.
- [ ] When another index with the same key specification but a different name and different options already exists (for example, a unique index coexisting with the non-unique index being renamed), that unrelated index is left untouched while the rename still succeeds.
- [ ] A conflict whose underlying index cannot be unambiguously identified (no name match, no single index matching the desired definition, and not resolved by observing a concurrent caller's result) still rethrows the original `MongoCommandException`, matching today's fallback behavior.
- [ ] When two concurrent calls race to resolve the same rename (including the case where one caller lists indexes after another has already dropped the old index but before it has recreated the new one), both calls complete successfully and the collection ends up with exactly one index matching the desired key specification and options.
- [ ] The session overload (`CreateOneOrUpdateAsync(session, model, options, cancellationToken)`) behaves the same as the non-session overload for all of the above.
- [ ] `docs/index-management.md` documents that a conflict is resolved by locating and dropping the existing index with the same key specification (not necessarily the same name), that an unrelated index sharing the same key specification is preserved, and that concurrent callers resolving the same conflict is tolerated.
- [ ] `dotnet build -c Release Chaos.Mongo.slnx` produces no warnings, and the complete existing and new test suite (including integration tests, via `bash ./build.sh Test`) passes while maintaining the repository's required merged line coverage.

## Technical Details

### Finding the real conflicting index

`IMongoIndexManager<TDocument>` exposes `DocumentSerializer` and `Settings` (giving `Settings.SerializerRegistry`), so the model's key specification can be rendered the same way `MongoEventStore.RenderFilter` (`src/Chaos.Mongo.EventStore/MongoEventStore.cs:131-138`) renders a filter:

```csharp
var renderedKeys = model.Keys.Render(new RenderArgs<TDocument>(indexManager.DocumentSerializer, indexManager.Settings.SerializerRegistry));
```

The model's **requested name** is the name the driver actually sent in the failed `createIndexes` command, `e.Command["indexes"][0]["name"]`: this equals `model.Options.Name` when the caller set it explicitly, and the driver's own computed default name (e.g. `Name_1`) otherwise. Reading it from the command rather than from `model.Options.Name` directly means a default-named index (where `Options.Name` is `null`) is identified correctly, without reimplementing the driver's default-naming convention. Today's bug is not this name itself, but trusting it as the *drop target*; here it is only one input into the lookup below, which still determines the actual index to drop by listing and matching, never by assuming this name identifies an existing index.

Two different normalized option sets are needed, both built from the same rendered keys and the same normalization rule — an omitted/null value on either side (an unset `CreateIndexOptions.Unique`/`Sparse`/`ExpireAfter`/`PartialFilterExpression`, or a `listIndexes` result document that omits the corresponding key entirely) compares equal to the server's documented default (`false` for `Unique`/`Sparse`, no expiry, no partial filter) — rendered through the same `RenderArgs` as the keys (seen in use for real indexes in `OutboxConfigurator.cs:46-50,57-66,70-79`), with `Collation` resolved to its effective document (the collection's default collation when neither side specifies one, otherwise the explicit `Collation`):

- **Identity options**: `Unique`, `Sparse`, `PartialFilterExpression`, `Collation`. These are exactly the options MongoDB treats as distinguishing two indexes that otherwise share the same key specification — it explicitly permits a unique and a non-unique index, a sparse and a non-sparse index, or indexes with different collations, to coexist on the same keys (see the [duplicate key pattern documentation](https://www.mongodb.com/docs/manual/core/index-unique/#basic-and-unique-indexes-with-duplicate-key-patterns) and [sparse/non-sparse coexistence](https://www.mongodb.com/docs/manual/core/index-unique/#sparse-and-non-sparse-unique-indexes)). Two indexes with the same keys and the same identity options cannot coexist under different names: the server raises `IndexOptionsConflict`/`IndexKeySpecsConflict` against the one that already exists, regardless of whether `ExpireAfter` also matches. The **identity definition** of an index or the desired model is its rendered keys plus its normalized identity options.
- **Effective options**: the identity options plus `ExpireAfter`. `ExpireAfter` (TTL) is not an identity option — the server does not require it to match before raising a conflict against a same-identity index filed under a different name, so an existing index's current TTL need not equal the desired one for it to be the conflicting index. The **effective definition** of an index or the desired model is its rendered keys plus its normalized effective options.

`BsonDocument` equality is structural, which lets normalized definitions be compared. Define two distinct predicates over an existing index and the desired model, instead of one ambiguous "equivalent" notion that was previously used for both purposes:

- **Fully satisfies the request**: the existing index's name equals the requested name, and its effective definition equals the model's effective definition (including `ExpireAfter`). An index that fully satisfies the request is the desired end state already in place — including its TTL — and is never a drop candidate.
- **Matches the desired definition** (name-independent): the existing index's identity definition equals the model's identity definition, regardless of its name and regardless of whether `ExpireAfter` also matches. This identifies the index that is, in every way the server treats as identity-distinguishing, the index the caller is trying to create — just filed under a different name, and possibly with a different TTL that the drop-and-recreate below corrects. A bare key match cannot by itself identify the index the server is actually complaining about, because MongoDB permits more than one index with the same keys but different identity options to coexist (for example a unique and a non-unique index on the same field) — only an identity-definition match can, which is also why the server raises this conflict exactly when such a match exists under a different name, independent of `ExpireAfter`.

On `IndexOptionsConflict`/`IndexKeySpecsConflict`, list the existing indexes (`indexManager.ListAsync(cancellationToken)`, or the session overload) and resolve the conflicting index as follows, instead of trusting `e.Command["indexes"][0]["name"]` as the drop target:

0. If any existing index already fully satisfies the request, the desired end state already exists (a concurrent caller finished first); return that index's name without dropping anything.
1. Otherwise, if an index with the requested name exists, that is the conflicting index — step 0 already ruled out a full match, so this index's effective definition must differ from the desired model's, in keys or in any effective option including possibly only `ExpireAfter` (this preserves today's existing same-name replacement behavior exercised by `CreateOneOrUpdateAsync_WhenIndexExistsWithDifferentKeySpecs_ShouldDropAndRecreate` / `..._WhenIndexExistsWithDifferentOptions_ShouldDropAndRecreate` and their session equivalents).
2. Otherwise, look for indexes that match the desired identity definition (name-independent, as defined above), ignoring `ExpireAfter`. If exactly one such index exists, that is the conflicting index (this is the rename case: same identity definition, different name, possibly also a different `ExpireAfter` that the recreate corrects — an unrelated same-key index such as a differently-configured unique index does not match the desired identity definition and is correctly left as a non-candidate). If more than one exists, the conflict is ambiguous — do not drop any of them.
3. If no candidate is identified by either step (ambiguous, or none found), do not immediately rethrow; a concurrent caller may be mid-flight (see below) before concluding the conflict is genuinely unidentifiable.

### Tolerating concurrent resolution

Drop the identified candidate through `DropOneIfExistsAsync` (already in this file, `:92-95` and `:129-133`) rather than a raw `DropOneAsync`, so a concurrent caller that already dropped the same index does not fail this call. Then retry `CreateOneAsync`.

Two points in this flow can race with a concurrent caller performing the same resolution, and both must converge on success rather than a spurious throw:

- **No candidate found in step 3 above.** This can mean the conflict is genuinely unidentifiable, or it can mean a concurrent caller already dropped the old index but has not yet recreated the new one, so neither the old nor the new index is present to match against. Before rethrowing, retry `CreateOneAsync` once: if it now succeeds (the concurrent caller finished), return its result. If it conflicts again, re-list and check whether an index now exists that fully satisfies the request (as defined above); if so, the desired end state already exists, so return that index's name instead of throwing. Only rethrow the original exception once this recheck also fails to identify or observe the desired state.
- **The retried `CreateOneAsync` after this call's own drop still conflicts** (a concurrent caller recreated the index between this call's drop and create). Re-list and check whether an index now fully satisfies the request: if so, return its name instead of throwing. If none is found, rethrow — a genuine, unresolved conflict remains.

This mirrors the existing idiom in this codebase for tolerating a concurrent actor having already produced the same end state (e.g. `AnchorEvidenceStore.InsertIfAbsentAsync` catching `DuplicateKey` and treating it as success, `src/Chaos.Mongo.EventStore/Integrity/AnchorEvidenceStore.cs:174-183`), applied here to index conflicts instead of write conflicts.

### Shared helper, both overloads

Both `CreateOneOrUpdateAsync` overloads (session and non-session) need the same list-and-match logic. Add a private helper parameterized on the listing delegate, following the existing `ExecuteDropOneAsync(Func<Task> dropOne)` pattern (`:156-166`), e.g. a `FindConflictingIndexNameAsync` taking a `Func<Task<IAsyncCursor<BsonDocument>>>` lister, the requested name, and the rendered key/options comparison, implementing the full-satisfaction-then-name-match-then-definition-match-then-ambiguity rules above, so the session and non-session call sites differ only in which `ListAsync`/`DropOneAsync` overload they pass in.

### Out of scope

`MongoEventStoreConcurrencyIndexSupport.CreateIndexAsync` (`src/Chaos.Mongo.EventStore/MongoEventStoreConcurrencyIndexSupport.cs:78-86`) has the same `e.Command["indexes"][0]["name"]` pattern, but only uses it to build an error message and never drops/replaces the index. It is not part of this issue's scope and is left unchanged.

### Testing

The existing integration tests in `tests/Chaos.Mongo.Tests/Integration/MongoIndexManagerExtensionsIntegrationTests.cs` cover create-when-missing and conflicts under the same name; these existing tests must keep passing unmodified (they pin the same-name replacement behavior from step 1 of the lookup). Extend the class with:

- A rename scenario: create an index under one name, then call `CreateOneOrUpdateAsync` with the same keys under a different name, and assert the old name is gone and the new name exists with the expected definition.
- A rename-plus-TTL scenario: create an index under one name with `ExpireAfter` set to one value, then call `CreateOneOrUpdateAsync` with the same keys and the same identity options (`Unique`/`Sparse`/`PartialFilterExpression`/`Collation`) but a different name and a different `ExpireAfter` value; assert the old name is gone and the new name exists with the new `ExpireAfter` value. This is the case step 2's identity-only matching exists for: the existing index's `ExpireAfter` differs from the desired one, so it cannot be found via the "fully satisfies" predicate, but it must still be identified as the conflicting index via identity-only matching, not left in place by an unidentifiable-conflict rethrow.
- A coexisting-index scenario: create a unique index and a separate non-unique index with the same key specification but different names (per the MongoDB-supported duplicate-key-pattern configuration), rename the non-unique one via `CreateOneOrUpdateAsync`, and assert the unique index is untouched while the rename still succeeds.
- A Sparse-option scenario: under the same-name case (same name, `Sparse` flips between calls) and under the rename case (two same-key, same-`Unique` indexes differing only by `Sparse`, under different names), assert `CreateOneOrUpdateAsync` replaces only the index whose identity definition actually differs from, or matches, the desired one, leaving a differently-`Sparse` sibling untouched where one exists.
- A Collation scenario: two same-key indexes with different explicit `Collation` values under different names; renaming to the one matching the desired model's collation asserts only the matching index is replaced and the other is untouched.
- A default-name scenario: create an index with `Options.Name` left unset (the driver's default-generated name), then call `CreateOneOrUpdateAsync` again with the same keys, no explicit name, and different options; assert the default-named index is replaced rather than left alone or mistaken for an unrelated index.
- A concurrency scenario: with an existing index already needing the same rename, issue multiple concurrent `CreateOneOrUpdateAsync` calls (e.g. via `Task.WhenAll`) for the same target model and assert none throw and the collection ends with exactly one index matching the desired keys/options.
- Session-overload equivalents of all scenarios above, consistent with the existing pattern of parallel session/non-session test cases in this file.

Two internal branches are timing-dependent against a real server and cannot be reliably forced through Testcontainers. Per `tests/AGENTS.md`, cover both directly with a hand-crafted fake `IMongoIndexManager<TDocument>` (solitary tests), since they are otherwise unreachable deterministically:

- The retried `CreateOneAsync` after this call's own drop conflicts again, and a matching index is found by re-listing: the fake returns a conflict from the first `CreateOneAsync`, a `listIndexes` result for the old name, success from `DropOneAsync`, a second conflict from the retried `CreateOneAsync` (simulating a concurrent caller), and a `listIndexes` result now showing the desired index — asserting the call returns that name without throwing.
- The initial lookup finds no identifiable candidate because a concurrent caller has already dropped the old index but not yet recreated the new one: the fake returns a conflict from the first `CreateOneAsync`, a `listIndexes` result containing neither the old nor the new index, and then either a successful `CreateOneAsync` on recheck, or a second conflict followed by a `listIndexes` result now showing the desired index — asserting the call returns successfully in both variants rather than rethrowing.
