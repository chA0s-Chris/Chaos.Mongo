# Handle queue handler cancellation and shutdown correctly

## Rationale

[Issue #237](https://github.com/chA0s-Chris/Chaos.Mongo/issues/237) reports that `MongoQueueSubscription<TPayload>.ProcessQueueItemAsync` (`src/Chaos.Mongo/Queues/MongoQueueSubscription.cs`) cannot distinguish a handler-caused cancellation (e.g. an `HttpClient` timeout inside the payload handler) from a subscription shutdown, because it treats every `OperationCanceledException` as shutdown. This has three effects: a handler's own timeout is swallowed without a log entry and without counting against `MaxRetries` (`:335` filters out all `OperationCanceledException`, and the empty catch at `:374` repeats the mistake); an item whose handler finishes right as shutdown begins can lose its completion write because that write (`:344-352`) uses the already-cancelled token, so it reappears and reruns after the lease expires; and an item whose handler is genuinely cancelled by shutdown stays locked for the full lease (5 minutes by default) instead of becoming available again immediately.

The fix distinguishes shutdown-caused cancellation from handler-caused cancellation using the inbound `cancellationToken`'s `IsCancellationRequested` state, and performs the completion write and the shutdown lock release with a token that is not tied to that same cancellation source, so they can still complete during shutdown.

## Acceptance Criteria

- [x] When the payload handler throws an `OperationCanceledException` (e.g. `TaskCanceledException` from an internal timeout) while the `cancellationToken` passed to it has **not** been cancelled, the item is treated as a failure: it is logged through the existing failure path and its retry count is incremented, so `MaxRetries` is respected.
- [x] When the payload handler throws (or is observed to throw) an `OperationCanceledException` while the `cancellationToken` **has** been cancelled (subscription shutdown), the item's lock is released immediately instead of being left locked for the remainder of the lease, and this does not count as a retry attempt.
- [x] When the payload handler completes successfully but the `cancellationToken` is already cancelled by the time the completion write (close/delete) runs, the completion write still succeeds and the item is not reprocessed on the next poll.
- [x] An item released after a shutdown-caused cancellation is selected by `CreateAvailableQueueItemFilter` again as soon as the lock-release write is visible, without waiting for `LockLeaseTime` to elapse.
- [x] Automated tests cover: a handler-caused cancellation while `cancellationToken` is not cancelled (failure path, retry increment, log entry); a shutdown-caused cancellation (lock released, no retry increment); and a successful handler completion where `cancellationToken` is already cancelled before the completion write (completion still recorded).
- [x] The Release build (`dotnet build -c Release Chaos.Mongo.slnx`) has no warnings and the full test suite passes.

## Technical Details

- In `ProcessQueueItemAsync` (`src/Chaos.Mongo/Queues/MongoQueueSubscription.cs:277-379`), replace the handler's `catch (Exception e) when (e is not OperationCanceledException)` (`:335`) with two catch clauses, evaluated in order:
  1. `catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)` — confirmed shutdown. Release the item's lock (see below) and `return`.
  2. `catch (Exception e)` — everything else, including a handler-caused `OperationCanceledException` observed while `cancellationToken` is not cancelled. Call the existing `HandleFailedQueueItemAsync(collection, queueItemId, acquiredLockUtc, e, cancellationToken)` and `return`, unchanged from today's failure handling.
- Add a private helper (e.g. `ReleaseLockForShutdownAsync`) that clears the lock for a shutdown-cancelled item using `CreateLockOwnershipFilter(queueItemId, acquiredLockUtc)` with an update of `Set(x => x.IsLocked, false)` / `Unset(x => x.LockedUtc)`. It must not increment `RetryCount` — this is an interruption, not a failed attempt. Log a warning (parallel to the existing "lock ownership changed" warnings) when the ownership filter matches zero documents, and log/swallow any exception from the write itself so a failed release degrades to the existing lease-expiry recovery instead of throwing out of `ProcessQueueItemAsync`.
- Because `cancellationToken` is already (or about to be) cancelled whenever this helper runs, and the same token is also no longer trustworthy for the success-path completion write at `:342-352`, both operations must use a separate `CancellationToken` that is not linked to `cancellationToken` or to `_cancellationTokenSource`. Create it from a short-lived `CancellationTokenSource` with a fixed timeout (new internal constant, e.g. `MongoQueueSubscriptionDefaults.CompletionGraceTimeout`, a few seconds) so these two writes get a bounded grace period to reach MongoDB even after shutdown has been signalled, without risking an indefinite hang if the connection is unavailable. `MongoQueueSubscriptionDefaults` is `internal`, so this is not a public API change.
- `HandleFailedQueueItemAsync`'s own writes (retry increment, terminal transition) keep using the caller's `cancellationToken` — that method now only runs for confirmed handler failures (not shutdown-caused cancellation), matching today's behavior.
- The outer `catch (OperationCanceledException) { }` at `:374` remains to cover cancellation surfaced outside the handler invocation (e.g. the lock-acquisition `FindOneAndUpdateAsync` at `:288` observing an already-cancelled token before any lock was taken, or the grace-period token itself expiring); no item lock exists yet in the first case, so silently returning stays correct there, but a failed grace-period write is a real operational condition and should be logged rather than silently swallowed.
- No public API, configuration surface, or `MongoQueueDefinition`/`IMongoQueueSubscription<TPayload>` contract changes. All changes stay inside `MongoQueueSubscription<TPayload>` and its internal defaults.
- Tests live in `tests/Chaos.Mongo.Tests/Queues/MongoQueueSubscriptionTests.cs`, which already invokes `ProcessQueueItemAsync` and `HandleFailedQueueItemAsync` by reflection against hand-written `IMongoCollection<MongoQueueItem<TestPayload>>` fakes (e.g. `CompletingQueueItemCollection`) and `Mock<ILogger<...>>` assertions; follow that existing pattern (a fake collection that records which filter/update it received per call, or a dedicated per-scenario fake) rather than introducing a new mocking framework. Confirm the two existing handler-cancellation tests (`ProcessQueueItemAsync_WhenHandlerIsCanceled_StillDisposesItemScope`, which currently cancels with `CancellationToken.None`) still hold under the new branching — that test now exercises the handler-caused-failure path rather than the old blanket-swallow path — and adjust/extend them as needed to assert the new behavior (retry increment call, or logged failure) instead of only scope disposal.
