# Stop components safely when two stops overlap

> Issue: [#313](https://github.com/chA0s-Chris/Chaos.Mongo/issues/313)

## Rationale

`OutboxProcessor`, `EventStreamSealingSweep`, `IntegrityAnchoringService` and `MongoQueueSubscription` stop their background loop by cancelling a `CancellationTokenSource`, waiting for the loop, and disposing the source. When two stops overlap, the second `CancelAsync()` returns at once because cancellation is already requested, even though the first is still running its callbacks. If the second stop then disposes the source, the first stop's callbacks that have not run yet can be dropped: token-based waits never wake, and in the outbox the callback that arms the finalization grace period never runs. The first stop's own cleanup can then throw a `NullReferenceException` on the field the second stop cleared (the queue subscription's `DisposeAsync` has the dropped-callback problem too, and disposes the source and semaphore while the loops may still use them). Overlap is realistic for the public components: `IOutboxProcessor.StopAsync` and `IMongoQueue.StopSubscriptionAsync` (which drives the internal `IMongoQueueSubscription<TPayload>`) are public entry points, and `OutboxProcessor.StartAsync` already warns about processors started both automatically and manually.

Separately, a callback registered on a token that is being cancelled can throw, which faults `CancelAsync()` with an `AggregateException` that escapes from the cancelling code. This replaces the real outcome of `AnchorCompletionNotifier.InvokeHookAsync` and fails the stop paths. #312 solved this in `MongoMigrationRunner` (`SignalLockLostAsync`) by logging the failing callback; the same treatment applies here.

The goal is that each stop path runs exactly one stop operation, however many callers overlap, that no callback is dropped and no stop throws because of an overlap, that a caller's shutdown timeout is still honored, and that a failing cancellation callback is logged instead of replacing the actual outcome. This also completes the `CancelAsync()` audit that #312 left open for these components.

## Acceptance Criteria

- [ ] `OutboxProcessor.StopAsync`, `EventStreamSealingSweep.StopAsync` and `IntegrityAnchoringService.StopAsync`, called while another stop of the same instance is still running its `CancelAsync()` callbacks, neither drop those callbacks nor throw. This holds even when the second caller's token is already cancelled: every callback registered on the loop token runs, and both calls complete without exception.
- [ ] A stop caller whose token is cancelled before the loop has finished returns without exception, as today, and while the loop is still running leaves the instance in the "stopping" state: the token source is not disposed and the fields are not cleared until the loop has finished, even after every cancellation callback has completed. The loop then still observes the cancellation.
- [ ] `MongoQueueSubscription.StopAsync` and `DisposeAsync`, in any overlap (stop/stop, stop/dispose, dispose/dispose, dispose while a stop caller has timed out), share one stop operation. No callback registered on the stopping token is dropped, and `_cancellationTokenSource` and `_signalSemaphore` are released exactly once, only after the monitor and processing tasks have finished. Releasing is tied to the tasks, not to the callbacks: while a handler or collection operation keeps a processing or monitor task running after every cancellation callback has completed, `DisposeAsync` stays pending and nothing is released. `DisposeAsync` completes only after the tasks have finished, and `StopAsync` during an in-progress `DisposeAsync` joins the operation, bounded by its own token, instead of returning at once (an uncancelled `StopAsync` stays pending until the tasks have finished). `DisposeAsync` logs and swallows a faulted loop instead of throwing.
- [ ] `MongoQueueSubscription` disposal or stop that arrives while `StartAsync` is still running (after the subscription is marked active, before both background tasks are published) waits for startup to finish: neither disposes resources startup still uses nor leaves a cursor opened by startup undisposed, and the existing late-startup-cancellation behavior stays as it is.
- [ ] `IMongoQueue.StopSubscriptionAsync(token)` still honors its token as the shutdown timeout: once the call has acquired the queue's own `_semaphore` and has stopped or joined the subscription's disposal, a handler that ignores cancellation and a token that expires during that disposal make it return without exception, with the subscription retained as stopping, and the subscription's resources are released once the handler finishes. The acquisition of `_semaphore` stays cancellable as today and is not part of that guarantee: a token that is already cancelled on entry, or that expires while another start or stop holds `_semaphore`, still ends the call with `OperationCanceledException` before it runs any stop work, and any shutdown already in flight is left to finish on its own. `StartSubscriptionAsync` never creates a replacement subscription while the previous one is still shutting down: its wait for the previous subscription is bounded by its own token, and a timeout there surfaces as cancellation of the start.
- [ ] A cancellation callback that throws while a stop path cancels its token does not make `StopAsync` or `DisposeAsync` throw. The failure is logged as a warning that carries the exception `CancelAsync` surfaced (an `AggregateException` whose inner exception is the callback's), the loop is still joined, and the instance still ends up stopped.
- [ ] `AnchorCompletionNotifier.InvokeHookAsync` / `KeepLockAliveAsync` with a cancellation callback that throws: (a) on genuine lock loss (refused extension, or an extension that throws) the hook is still cancelled, `NotifyAsync` returns `false` and the anchor is not marked notified; the refused-extension path does not log "could not be extended" for the callback's failure; the extension-failure path keeps the warning that carries the actual extension exception; the callback's failure is logged as a separate warning carrying the surfaced `AggregateException` with the callback's exception as inner exception. (b) A throwing callback on the `hookCompleted` token does not change the outcome already determined by the hook or by the caller's cancellation (a hook that returned normally still yields `true` and the anchor is marked notified), and the keep-alive task is still joined.
- [ ] Behavior outside overlapping or failing stops is unchanged: a single stop still stops the loop and releases its resources, a stop on a never-started or already-stopped instance still returns immediately, and an instance can be started again after a completed stop (outbox processor, sealing sweep, anchoring service), including when the first stop completed synchronously (the new run's stop is never satisfied by the previous run's completed stop). All existing tests pass unchanged.
- [ ] Each of the four components has a regression test with overlapping stops (queue subscription: also stop/dispose, dispose/dispose, the startup/disposal interleaving, and the `MongoQueue` timeout case), and the notifier has tests for the outcomes listed above. The overlap tests are specified in Technical Details ("Tests"). Each of them fails against the original stop logic and passes with the fix: the implementer verifies this by running them against the original stop logic (reverted locally through a temporary copy or WIP commit, never a bare `git stash`, and not committed) and leaves a short note outside Git, `/srv/factory/workflow-state/<task-id>/overlap-test-evidence.md`, naming each test and its observed failure message, which the code reviewers read.
- [ ] `./cleanup_code.sh` has been run and its diff inspected, `dotnet build -c Release Chaos.Mongo.slnx` reports no warnings or errors, `./inspect_code.sh --base <actual base at execution>` reports no findings at warning or error severity, and one complete Docker-backed `bash ./build.sh Test` run (via the Factory runner; it runs every test project with coverage) passes, which establishes both the complete-suite result and the build's coverage gate (merged and per-package thresholds in `CoverageThresholds`). No second `dotnet test` of the solution is run.

## Technical Details

**Stop contract (outbox processor, sealing sweep, anchoring service).** The first caller starts one stop operation for the current run and later callers await that same task. The operation cancels the loop's token source (through the logging helper below), joins the loop, and only then disposes the source and clears the fields, so it runs to completion independent of any caller's token. Each caller bounds its own wait with `WaitAsync(cancellationToken)` and keeps swallowing the resulting `OperationCanceledException` as today. A non-cancellation exception from the loop still reaches the awaiting callers after the cleanup. State checks, publication of the operation, cleanup and the check-and-set in `StartAsync` use one gate (a lock around state transitions, never held across an await), so an overlapping `StartAsync` cannot observe half-cleared fields.

*Publication invariant.* The shared operation of the current run must be visible to every caller (and to `StartAsync`) before any stop work or cleanup can run, and cleanup must clear only the operation and sources that belong to the run it finishes. The operation therefore must not start running synchronously inside the gated assignment: an `_stopOperation ??= StopCoreAsync()` shape is wrong because a loop that has already finished and a source without pending callbacks let the core run to completion (and clear the field) before the assignment stores the finished task, which the next run's stop would then reuse. Create the operation so its work begins only after it has been published (for example a `TaskCompletionSource` published under the gate with the core started by the publishing caller after the gate is released, or an equivalent), and have cleanup compare against the run's own state. The operation also observes its own fault (every caller may have abandoned its wait through its token), so a faulted stop never surfaces as an unobserved task exception. A start/stop/restart test must stop the new run after a synchronously completing first stop.

**Stop contract (queue subscription).** `StopAsync` and `DisposeAsync` share one stop operation under the same gate and publication invariant. `StopAsync` bounds its wait with its token (keeping the "background tasks may still be running" warning). `DisposeAsync` marks the subscription disposed, creates or joins the stop operation, awaits it without a token, logs and swallows a loop fault, and then releases `_cancellationTokenSource` and `_signalSemaphore` exactly once (one release owner, shared by concurrent dispose callers); stop alone does not release them, as today. Startup handoff: `StartAsync` marks the subscription active, then awaits index creation and the change-stream open before it releases the startup signal, reads the stopping token and publishes `_monitorTask` and `_processingTask`; it must publish its own completion (for example a completion source created under the gate in the same critical section that sets `_isActive`, completed in a `finally`) and the stop operation awaits an in-flight startup (ignoring its outcome, which belongs to the `StartAsync` caller) before it joins the two tasks and before resources may be released. A stop or dispose therefore either observes the published pair of tasks or runs after startup has finished with its resources and cursor handed to the monitor delegate (which keeps owning and disposing the pre-opened cursor). `StartAsync` keeps reading the stopping token before scheduling the delegates (the #238 fix); the existing start-versus-dispose tests, including `MongoQueueSubscriptionTests.StartAsync_StartupCanceledAfterChangeStreamOpens_StartsLoopsAndDisposesCursorOnStop`, must keep passing.

**`MongoQueue` and the public timeout.** `IMongoQueue.StopSubscriptionAsync(token)` documents its token as a shutdown timeout and `MongoHostedService.StoppingAsync` forwards the host token to it, so the disposal wait must not become unbounded behind it. `StopSubscriptionAsync` bounds the post-stop `DisposeAsync()` by the caller's token (`DisposeAsync().AsTask().WaitAsync(token)`), swallows that cancellation as the subscription's `StopAsync` already does, and on a timeout keeps `_subscription` (inactive, still shutting down) instead of clearing it, so `_semaphore` is released and a later stop or start joins the same shutdown; `_subscription` is cleared only after a completed dispose. `StartSubscriptionAsync` bounds its dispose of an inactive subscription the same way but lets the cancellation propagate and keeps `_subscription`, so no replacement subscription is created beside loops that are still running. `MongoQueue.DisposeAsync` (no token) keeps waiting for the shutdown. The `_semaphore.WaitAsync(cancellationToken)` at the top of both methods is untouched: it is the existing, documented cancellable acquisition, so the timeout guarantee above covers only a call that got past it, and a cancellation before or during that acquisition keeps throwing `OperationCanceledException` without entering the body. The abandoned bounded wait leaves the subscription's own stop operation running, which finishes the disposal and observes its own outcome (`DisposeAsync` swallows a loop fault), so a timeout never produces an unobserved task exception or a leaked resource.

**Intended behavior changes, to disclose in the PR.** (1) A stop whose caller timed out no longer frees the instance: the source and fields are cleared only when the loop finishes, so `StartAsync` during that window is treated as "already running" (the same check it already does between `CancelAsync` and cleanup today) instead of starting a second loop beside the old one. (2) `MongoQueueSubscription.DisposeAsync` now waits for the monitor and processing tasks, as the issue proposes, where it used to return without waiting; `MongoQueue.StopSubscriptionAsync` and `StartSubscriptionAsync` bound that wait by their caller's token as described above, so the public timeout contract is kept, while `MongoQueue.DisposeAsync` and a direct `DisposeAsync` of the internal subscription wait for the handler to finish.

**Failing callbacks.** `CancelAsync` still runs every registered callback and aggregates their exceptions, so catching the fault after the fact is safe: cancellation has been requested either way. Each cancelling site calls one small internal helper that catches the exception from `CancelAsync`, logs a warning naming the component, and continues. The helper is not shared across assemblies: no production sibling package is among the repository's `InternalsVisibleTo` entries (they name test, benchmark and load-test assemblies and the proxy assembly), and widening `Chaos.Mongo` to its sibling packages would couple their versions through internals. `Chaos.Mongo.EventStore` gets one helper used by the sweep, the anchoring service and the notifier; `Chaos.Mongo.Outbox` and `Chaos.Mongo` (queue subscription) cancel through their own private equivalent, as `MongoMigrationRunner.SignalLockLostAsync` already does. The implementer may extract the shared stop logic of the sweep and the anchoring service (identical today) within `Chaos.Mongo.EventStore`; the extraction is not required. Stop paths cancel through the helper inside the stop operation, so a failure never reaches a caller.

*Notifier outcomes.* `hookCompleted` is cancelled in `InvokeHookAsync`'s `finally` and its token also reaches `ensureLockAsync` and `Task.Delay` in `KeepLockAliveAsync`, so a hook may return normally while a lease-check callback is still registered. Cancelling `hookCompleted` through the helper therefore preserves whatever the hook or the caller's cancellation already determined (including success) and still awaits `keepAlive`. Cancelling `hookCancellation` through the helper on the refused-extension and `catch (Exception)` paths keeps the lock-loss result (`false`, anchor not marked notified); the actual extension exception stays distinct from a callback warning.

**Affected code (verified at the plan's base commit).** `OutboxProcessor.StartAsync`/`StopAsync` (`_cancellationTokenSource`, `_processingTask`); `EventStreamSealingSweep.StartAsync`/`StopAsync` (`_sweepLoop`); `IntegrityAnchoringService.StartAsync`/`StopAsync` (`_loop`); `MongoQueueSubscription.StartAsync`/`StopAsync`/`DisposeAsync` (`_cancellationTokenSource`, `_signalSemaphore`, `_monitorTask`, `_processingTask`, `_isActive`, `_isDisposed`); `MongoQueue.StartSubscriptionAsync`/`StopSubscriptionAsync` (`_subscription`, `_semaphore`); `AnchorCompletionNotifier.InvokeHookAsync`/`KeepLockAliveAsync` (`hookCancellation`, `hookCompleted`).

**Audit completion.** The remaining `CancelAsync()` call sites in `src/` stay unchanged: the linked `raceCancellation` in `MongoQueueSubscription.WaitForSignalOrIntervalAsync` is awaited and only the semaphore and delay registrations hang off it, and `MongoMigrationRunner` was handled by #312. Re-grep `CancelAsync` over `src/` during implementation for the PR description, so the list is current.

**Tests.** Hand-crafted doubles, no new Moq usage; sociable tests through the public `StopAsync`/`DisposeAsync` (see `tests/AGENTS.md`). The deterministic hold: register a callback that blocks on a barrier the test releases on the token the loop passes to a test double (the publisher's, the lock's or the handler's token; for the outbox a hand-crafted `IOutboxPublisher`, since the fixture's publisher is a Moq mock). Callbacks run sequentially in reverse registration order, so for each component register a marker callback first and the blocker second, back to back in the same synchronous double call so both land in the same callback partition (ordering is only guaranteed within one registering thread's partition): the blocker runs first and holds stop A while the marker is still pending. The outbox's own finalization-grace-period callback is registered later than a publisher-side blocker and therefore is not pending in this setup; assert it only where the registration order really allows it. The assertions observe completion ordering and resource ownership, not callback loss alone, because the runtime may already have taken the registration list before the first callback runs (so a dropped callback is not reproduced by every schedule, while the double-cleanup exception and early disposal are); release every barrier in a `finally` so a failing assertion cannot hang the run:

- stop/stop (outbox, sweep, anchoring): while A is held, a second caller with an already-cancelled token returns without exception before the barrier is released; after the release both operations complete, the marker callback ran, nothing threw, and the instance can be started and stopped again.
- timed-out stop keeps ownership (outbox, sweep, anchoring; the "stopping" state of the second criterion): use a test double whose operation ignores cancellation until the test releases it (the publisher, lock or `IMongoHelper` double), so the loop outlives every callback. Phase one: a stop with an already-cancelled token returns without exception, every callback has run, and the instance is still "stopping" (a `StartAsync` is treated as "already running" and creates no second loop). Phase two: release the operation; the loop ends, the source and fields are cleared, and the instance starts and stops again.
- queue subscription stop/stop: arrange for both loop tasks to finish independently of the still-blocked callback; an uncancelled second `StopAsync` stays pending until the barrier is released; a second caller with a cancelled token returns and logs the existing warning.
- queue subscription stop/dispose, dispose/stop and dispose/dispose: `DisposeAsync` stays pending while the barrier holds, the source and semaphore remain usable (not disposed) until the operation finishes, and are released exactly once afterwards.
- queue subscription resource lifetime after the callbacks: one scenario holds a handler (or a collection operation) that ignores cancellation, independent of any callback barrier, so every cancellation callback completes while the processing task is still running. Phase one: observe that cancellation completed (the stopping token is cancelled and its callbacks ran), then assert `DisposeAsync` is still pending, the source and semaphore are not released, and, for dispose-first/stop-second, that an uncancelled second `StopAsync` is still pending too (this catches an early return while disposal is in progress). Phase two: release the handler, then assert disposal and the second stop complete and resources are released exactly once. Run it as stop-then-dispose and as dispose-first/stop-second.
- evidence discipline for the pending assertions (all of the above, including the public queue case): a pending assertion observes the call through a bounded outer wait that does not use the tested token (for example `Task.WhenAny(call, Task.Delay(<short>))`) and never awaits an unbounded `DisposeAsync` directly while a barrier is held, because the base wrapper awaits disposal without a token and would otherwise hang the test before the `finally` that releases the barrier; completion awaits after the release use a generous `WaitAsync` timeout, so a regression fails the test instead of hanging it.
- queue subscription startup/disposal: use the existing controlled collection double (`ObservedPollingCollection` in `MongoQueueSubscriptionTests`: `HoldOpen` pauses `WatchAsync` before the cursor is returned, `OpenStarted` reports that startup is suspended, `AllowOpen` releases it) so the change-stream open can be held; call `DisposeAsync` while startup is suspended, then release it; assert both tasks were published and the cursor disposed once, dispose completes, and nothing touched a disposed resource.
- `MongoQueueTests`: a subscription double whose disposal waits for a handler that ignores cancellation; `StopSubscriptionAsync` with a token that expires during that disposal returns, `_subscription` is retained, `IsRunning` is false, a following `StartSubscriptionAsync` with a short token is cancelled without creating a second subscription, and after the handler finishes a stop completes disposal and clears it. A separate pre-cancelled-entry case documents the unchanged acquisition semantics: with a token already cancelled on entry (and, as a second case, a token that expires while another stop holds `_semaphore`), `StopSubscriptionAsync` throws `OperationCanceledException` without touching the subscription, and the in-flight shutdown still completes later.
- throwing callbacks: register a throwing callback on the same token and assert the warning with the surfaced `AggregateException` and its inner callback exception through a recording logger double (`CapturingLogger<T>` exists in `Chaos.Mongo.EventStore.Tests/Integration`); the sweep test keeps the unit-test form by using a hand-crafted `IMongoHelper` double whose `TryAcquireLockAsync` returns null (a seam taking the loop token).
- notifier: drive `NotifyAsync` through the existing controllable `ensureLockAsync` delegate and the `IntegrityAnchoringIntegrationTests` fixture (`LeaseCheckInterval` is already settable): a refused extension and an extension that throws, each with a throwing callback registered on the hook's token, and a successful hook with a throwing callback registered on the token the lease check received. Assert the return value, whether the anchor is marked notified, and the logged warnings' exception types and messages, not a phrase describing a real lock loss.

Place tests next to the existing ones: `OutboxProcessorTests`, `EventStreamSealingSweepTests`, `MongoQueueSubscriptionTests`, `MongoQueueTests`. `IntegrityAnchoringService` and `AnchorCompletionNotifier` have no unit tests today and are backed by MongoDB (`AnchorStore`, `AnchoringRun`), so their new tests follow `IntegrityAnchoringIntegrationTests` in the `Integration` folder with the `Integration` category and `TestDatabases` naming rules; a unit-level seam is acceptable only if it needs no production-visible change beyond `internal`. Checks follow `AGENTS.md` and the Factory execution contract: cleanup, scoped inspection (against the actual base at execution), the release build, and one aggregate Docker-backed `bash ./build.sh Test` for the complete suite and merged coverage.

**No public API change.** `IOutboxProcessor.StopAsync` and `IMongoQueueSubscription.StopAsync` keep their signatures and documented meaning; their XML remarks gain a sentence that concurrent stops share one stop, and `PublicAPI.*.txt` and the approved public-surface files stay untouched. The consumer-facing queue entry point, `IMongoQueue.StopSubscriptionAsync`, keeps its timeout meaning.
