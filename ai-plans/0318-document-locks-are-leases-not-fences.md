# Document that distributed locks are leases, not fences

## Rationale

`MongoLock` is a lease lock without fencing. A holder that stalls past its lease (GC pause, process suspension, a slow call, clock skew) can resume and write after another instance has acquired the lock, and it cannot detect this before the write. The current documentation mentions the overlap window but understates its consequence and recommends a guard that cannot close it: `docs/distributed-locking.md` advises checking `IsValid` before exclusivity-sensitive changes, which only narrows the race, and `docs/migrations.md` says the lock "ensures only one application instance runs migrations at a time". The `IMongoLock` API remarks say nothing about the overlap at all. See [issue #318](https://github.com/chA0s-Chris/Chaos.Mongo/issues/318).

The goal is for readers of the API docs, the locking guide and the migration guide to learn that the lock coordinates work but does not guarantee mutual exclusion, and to be told how to make writes safe regardless: make them safe to repeat, or condition them on data. Documentation only; no behavior changes.

**Accuracy constraints for the wording.**

- Describe what the code does today. `MongoLock.IsValid` is a local comparison against the last known lease and client clock; extension and release are keyed on a per-acquisition token (already documented in `distributed-locking.md`). Do not claim the library renews locks automatically or detects loss before a write.
- **#317 status rule (single source for criteria, both guides and the PR description).** #317 (branch `0317-check-migration-lock-ownership-in-transaction`, not on `main` at planning time) adds an ownership check inside the migration transaction. Its local commit (`a458590`) declares only an `internal` interface (`ITransactionFencedLock`); the check is a write to the lock document, filtered on the acquisition token and unexpired lease, as the first server operation of the transaction, so MongoDB orders competing lock-document changes against the commit. A plain read of the lock, or an `IsValid` check, inside a transaction does not have that property and must not be described as a guard. Both guides keep the [#317](https://github.com/chA0s-Chris/Chaos.Mongo/issues/317) issue link and invent no API names. The implementer re-checks the publication target's current tip (`origin/main`, not a stale local `main`) before writing, inspecting its source as well as commit ancestry in case the change landed by squash. If #317 has not merged, both guides and the PR description call it a pending, migration-specific guard tracked by #317 ("once #317 lands"). If it has merged, they describe what actually shipped, limited to the supported transactional migrations and to effects that join the migration session, never as a public API unless it actually is one. Cite the issue link, not a commit or PR.
- Keep the guarding section short, as the issue asks. For the token-conditioned pattern, the short description covers both steps: (a) every acquisition of the data (claim or reclaim) replaces the token stored on the record, so an old holder's token no longer matches; (b) the later state update is a filter-based update that matches on the record's id and the claim's token and treats `MatchedCount == 0` as lost ownership. Without step (a), a stale holder whose token is still on the record would match after another instance acquired the lease. State that the guard protects only that conditioned update: in the outbox, for example, a late publish can still happen twice (see `transactional-outbox.md`, "Publishing Within the Lock Lease"), so the guard does not make side effects exactly-once. No example code is required; if one is added it is illustrative only and introduces no new library types.
- Note in the text that `IMongoLock.Id` is the lock name and not a per-acquisition token (already stated in the Lock behavior list), so a holder cannot use it as a fencing token; the token must be generated by the application and stored with the data.

**`IMongoLock` remarks.** Add a short paragraph (or `<para>` blocks, matching the existing style in `MongoMigrationRunner.cs` if multiple paragraphs are used) to the type's `<remarks>`. Leave members' docs unchanged unless a member remark contradicts the new text. In the type remarks, keep the statement that disposal waits for an in-flight `TryExtendAsync` call (see `MongoLock.DisposeAsync`), but drop the claim that the release uses the expiry that extension stored: `MongoHelper.ReleaseLockAsync` matches the lock name, holder and acquisition token only. In implementation, apply `./cleanup_code.sh` to the actual worktree after the C# edit and inspect its diff for unrelated changes; then run `./inspect_code.sh` (scoped, no `--all`).

**`docs/migrations.md`.** Rewrite the bullet at "A distributed lock ensures only one application instance runs migrations at a time" so it says the lock coordinates runs: normally one instance runs at a time, but a holder that stalls past its lease may overlap with a later holder, which is why migrations must be idempotent and safe to retry (link to the `Recommendations` list in the same page and to #317 for the transactional case). The bullet on background lease renewal and cooperative cancellation (currently lines ~119-126) also needs a wording correction, because it promises that on lost renewal the migration "is not recorded as applied, and its transaction (if any) is aborted". The runner (`MongoMigrationRunner`) only checks local validity and the loss signal (`EnsureLockStillValidAsync`) before inserting the history entry and again before `CommitTransactionAsync`; renewal signals cancellation independently (the renewal loop), and the exception path aborts only if the session still reports an active transaction and suppresses abort errors. So a stalled runner can pass the last local check and send a commit after takeover, and cancellation during an in-flight commit cannot guarantee rollback. Reword: loss detected at a pre-commit check stops the run before the history insert or before the commit is sent, so the entry is not durably recorded, and triggers transaction cleanup (on the non-transactional path the history insert itself follows the last local check and can still race); lease renewal and cancellation alone guarantee nothing about a commit already sent; keep the existing caveat for non-transactional effects; describe the transaction-coupled safeguard per the #317 status rule. Drop the clause "so the lock is released using the renewed expiry" (release matches lock name, holder and acquisition token, as in the `IMongoLock` remarks). The following cancelled-token clause ("in which case the lock may stay held until its lease expires") is also inaccurate once that premise is gone and must not be kept verbatim: `MongoLock.DisposeAsync` releases after the extension semaphore is free, a cancelled extension does not change the release filter, and `MongoMigrationRunner` only uses the caller's token (`extensionAbortCts`) to skip waiting for the in-flight extension. Either drop the clause or restate it as: cancelling the token passed to `RunMigrationsAsync` skips waiting for an in-flight renewal; release does not depend on that renewal; the lock stays held only if the release itself fails (disposal suppresses release errors), after which it expires with its lease. This matches `distributed-locking.md` (a renewal reaching the server after cancellation does not prevent release). Keep the rest of the bullet rather than duplicating it.
