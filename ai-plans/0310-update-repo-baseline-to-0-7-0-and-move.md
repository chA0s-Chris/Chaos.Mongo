# Update repo-baseline to 0.7.0 and move local code-style rules into CODESTYLE.md

> Issue: [#310](https://github.com/chA0s-Chris/Chaos.Mongo/issues/310)

## Rationale

`CODESTYLE.md` is a synced whole file of repo-baseline 0.1.0, so the repository's own code-style rules live in `AGENTS.md` and `src/AGENTS.md`, where a reader of `CODESTYLE.md` misses them. repo-baseline profiles 0.7.0 turn `CODESTYLE.md` into a managed `code-style` block followed by a local `### Repository-Specific Rules` section, and tool 0.2.0 replaces the former synced file with that block during `sync`.

The goal is to adopt tool 0.2.0 and profiles 0.7.0, collect the repository-wide code-style rules in `CODESTYLE.md`, and keep the repo-baseline check in CI working with the new tool.

## Acceptance Criteria

- [x] `CODESTYLE.md` consists of the `code-style` managed block followed by a local `### Repository-Specific Rules` section; none of the former whole-file content remains outside the block.

- [x] The root `AGENTS.md` keeps the target-framework and central-package-version rules, `src/AGENTS.md` keeps its project overview, and `tests/AGENTS.md` and `benchmarks/AGENTS.md` are unchanged.

## Technical Details

- Sync on this branch with `dotnet repo-baseline sync . 0.7.0`, which also updates `.repo-baseline.json`; Renovate's #308 only bumps the version and becomes obsolete once this merges. `sync` lists `CODESTYLE.md` as replaced because it was a synced file; the `### Repository-Specific Rules` section is added by hand afterwards, since `sync` writes only the block.
- The jump from 0.1.0 includes profiles 0.2.0 to 0.6.0. Review the whole synced diff against the tagged comparison `v0.1.0...v0.7.0` of the selected profiles and its notes: the annotated tag messages for v0.2.0 to v0.4.0, which have no GitHub releases, and the GitHub release notes from v0.5.0. Changes include, for example, `max_line_length = 180` and `xml_blank_line_after_pi = false` for MSBuild and XML files and `resharper_redundant_cast_highlighting = suggestion` in the `.editorconfig` block, removed `m_` naming entries in `.repo-baseline/ReSharper.DotSettings`, the file-type allowlist for `cleanup_code.sh --all`, the reworded `code-style-and-inspections` block in `AGENTS.md`, and in the shared `CODESTYLE.md` content the field-naming wording, the redundant-cast rule, the `Suppressing Inspections` section and the intro paragraph on `Repository-Specific Rules`. Explain in the PR any change that the tagged comparison does not account for.
- Rules to move: from the root `AGENTS.md` "General Rules for the Code Base", the rule that warnings are errors and code changes must not add warnings, and the rule on exposing types publicly only when consumers need them. The target-framework and `Directory.Packages.props` rules are project configuration and stay. From `src/AGENTS.md`, the whole "Naming of public types" section, including its list of existing exceptions and the `MongoDefaults` member naming. The public-type naming rules move although they cover only `src/`: they define the public API surface that consumers and reviewers see, so they belong next to the shared naming rules in `CODESTYLE.md`. In `CODESTYLE.md`, the moved section opens with "These naming rules apply to the public types of the production libraries under `src/`." It replaces "These rules cover public types."; the following sentence excluding internal types stays. Test-method naming and the other test and benchmark rules stay in their nested `AGENTS.md`, because they concern only how those projects are written. Inside Repository-Specific Rules, the two root rules are bullets, and the public-type naming rules form a `#### Naming of Public Types` subsection that opens with the scope sentence. Keep the wording, adjusting only what is needed for the rules to stand alone in `CODESTYLE.md`. When moving the warnings rule, drop its nullable clause, which the shared Nullability rule covers, and keep the Release/CI warnings-as-errors and no-new-warnings parts. None of them is expected to replace a shared rule; the warnings rule complements the shared nullability rule and `.repo-baseline/Common.props`.
- Run the whole-solution cleanup after the sync so that the new XML formatting rules apply to MSBuild files. If the cleanup commit breaks the build or the tests, for example because member reordering moved a static field initializer, fix the cause in a commit before it and regenerate the cleanup commit. If the cleanup changes nothing, there is no `style:` commit and no `.git-blame-ignore-revs` entry. The 0.7.0 inspection-setting changes only lower the redundant-cast severity and remove `m_` naming entries that the shared user naming rules already override, so a scoped `--base` inspection is enough and `--all` is not required. Record the cleanup commit's hash in `.git-blame-ignore-revs` in a later commit. The PR is merged with a merge commit, because a squash or rebase merge changes the hash; if the branch is rebased before merging, update the hash.
- CI: the current job clones the pinned release tag and runs `tool/sync.cs`, which no longer exists in 0.7.0, so the job must switch to the local tool as described in the repo-baseline README ("In CI"). Running in the workspace applies `global.json`, which pins SDK 11.0.100, so the job installs the .NET 11 SDK instead of 10.0.x. The tool targets `net10.0` with `RollForward=Major`, so it rolls forward to the .NET 11 runtime when no .NET 10 runtime is installed. Drop the comment about keeping the workspace's `global.json` away from the tool. The `result` job keeps `repo-baseline` in its `needs` and its step that fails when that job does not succeed.
- `CONTRIBUTING.md` already points to `CODESTYLE.md` for code style and needs no change.
