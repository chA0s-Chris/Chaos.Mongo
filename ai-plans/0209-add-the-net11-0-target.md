# Add the net11.0 Target

## Rationale

Since [#208](https://github.com/chA0s-Chris/Chaos.Mongo/issues/208) the three packages target `net10.0` only. .NET 11 is released, and its support ends around November 2028, like .NET 10 LTS, so consumers on .NET 11 should get a `lib/net11.0` asset. Adding a target framework is not a breaking change ([#209](https://github.com/chA0s-Chris/Chaos.Mongo/issues/209)). The work waited for the GA release because prerelease SDKs clash with `allowPrerelease: false` and warnings-as-errors in Release builds.

The goal is that every package ships `lib/net10.0` and `lib/net11.0`, built and tested on both runtimes with the dependency minimums from #208 unchanged for both targets. A trial with .NET 11 RC 3 (owner comment on the issue) found that only the test projects need a source change, and that running both frameworks in one test run can bring back a known Docker flake.

## Technical Details

### Targets and SDK

`Directory.Build.props` keeps the plural `TargetFrameworks` property and sets `<MainTargets>net10.0;net11.0</MainTargets>` as a literal list. `src/Directory.Build.props` and, through the root file, every test project already take `$(MainTargets)`, so no project file changes. `LatestTarget` is used only by `benchmarks/Directory.Build.props`. The benchmarks deliberately stay on `net10.0`, the LTS and lower target: moving them is neither requested nor needed. Because `LatestTarget` then no longer names the newest framework, keep its value and add a short comment that it now only selects the benchmark target. `build/Nuke.csproj` has its own `TargetFramework` and its `Directory.Build.props` does not import the parent, so it stays `net10.0` and needs the .NET 10 runtime next to the .NET 11 SDK.

`global.json` changes only `sdk.version` to `11.0.100`. SDK 10.0.403 cannot satisfy that pin, because `latestFeature` rolls forward only within the same major and minor version. The approved verification environment provides SDK 11.0.100 and the .NET 10 and .NET 11 runtimes (operator-bound before this round). Use it through the project wrapper. If a command still resolves another SDK, stop and report it instead of editing the pin or falling back to the old SDK.

### Dependencies stay as they are

`Directory.Packages.props` does not change, and no per-framework `Condition` is added. A scratch probe (SDK 11.0.100, Release, `Chaos.Mongo` only, outside this worktree) built both frameworks with zero warnings and packed `lib/net10.0` and `lib/net11.0`. The `net10.0` nuspec group was unchanged. The `net11.0` group listed only Binder, DependencyInjection, Options.ConfigurationExtensions, MongoDB.Driver and System.IO.Hashing, all at the existing minimums. The Microsoft.Extensions abstractions packages are missing from that group because the SDK prunes packages that the .NET 11 framework already provides. This is expected and satisfies "same minimums for both targets". Do not treat the missing entries as a regression, and do not add them back. Verify all three packages' nuspecs during implementation rather than relying on the probe. EventStore and Outbox also depend on the sibling `Chaos.Mongo` package; that dependency follows the pack version, has no entry in `Directory.Packages.props`, and none must be added.

The `renovate.json` rule from #208 already holds the `src/` minimums for Dependency Dashboard approval, so no Renovate configuration change is needed.

### Test projects: SYSLIB0066

On `net11.0`, `IStartupValidator` is obsolete (SYSLIB0066), and Release builds turn that into an error at `tests/Chaos.Mongo.Tests/MongoBuilderTests.cs` and `tests/Chaos.Mongo.Tests/MongoOptionsTests.cs`. Confirmed by the same scratch probe: these were the only two errors in the Release solution build. Suppress it with a scoped `#pragma warning disable`/`restore SYSLIB0066` around exactly those usages, with a comment giving the reason: the tests verify the synchronous startup validation that `ValidateOnStart` provides, and the suggested `IAsyncStartupValidator` replacement is not confirmed to exist on `net10.0` (confirm this against the .NET 10 reference assemblies; if it exists and exercises the same behavior, using it on both frameworks is an acceptable alternative). Do not put SYSLIB0066 into `NoWarn` of `tests/Directory.Build.props`, which would hide later uses in other tests. `src/` does not use the type.

### Running both frameworks in the Nuke pipeline

`BuildPipeline.Test.cs` runs `dotnet test` once per `*.Tests.csproj` with `SetLoggers($"junit;LogFilePath={testOutput}")`, one result file per project. With two frameworks the file would be shared and `ReportTestCountAndCoverage`, which reads `*.Tests.xml`, could silently count only one framework. The installed `JUnitTestLogger` 1.1.0 (Syncromatics) accepts only `LogFilePath` and `TestRunDirectory`; it has no `{framework}` token. Design: the `Test` target combines the project list with the framework list (`net10.0;net11.0`, taken from the project's target frameworks rather than a second hard-coded list where practical), calls `SetFramework(tfm)` for each combination and builds the log path itself, for example `<Project>.<tfm>.Tests.xml`, which still matches the `*.Tests.xml` glob. Nuke runs the combinations one after the other, so the two test hosts of a project never start Testcontainers at the same time. That is the mitigation for the Docker flake below, and the report needs no change beyond the new file names. Coverage results are merged across all runs already; check that the gate still evaluates the merged result.

The owner's trial saw 48 of 186 `Chaos.Mongo.Outbox.Tests` tests fail on `net11.0` within 8 seconds with Docker's `Conflict ... container ... is not running` in a combined run; the same framework alone passed. Each test process starts its own container through `MongoDbTestContainer` (no fixed name, no reuse), so Docker-side contention between two simultaneous test hosts is the likely cause. The per-framework sequential execution above removes that overlap by construction. Run the complete pipeline on the final code. If the failure still occurs, find the cause instead of adding test retries; do not change test code to tolerate a failed container or rerun until green. Say in the handoff whether it occurred. Real suite evidence comes from one entry point, `bash ./build.sh Test`; do not run `dotnet test Chaos.Mongo.slnx` in addition for the same coverage. The Nuke change needs `BuildPipeline.Tests` coverage only if it adds pure logic that can be separated from Nuke, as `CoverageThresholds` and `PublicKeyTokenCheck` are.

### C# 15 check

`LangVersion latest` becomes C# 15 once SDK 11.0.100 is the pin, for both frameworks. Library code built for `net10.0` compiles against the .NET 10 reference assemblies, so any use of a type or member that exists only in .NET 11 fails the build. Language features with runtime requirements that are not visible as a missing member are the open risk. Review the diff of `src/` since the last release and the SDK 11 language release notes. Since the plan changes no `src/` code, the expected result is "no new language feature used". The `net10.0` test run on the .NET 10 runtime provides the runtime evidence. Do not pin `LangVersion` to an older value to avoid the question.

### Workflows

`ci.yml` has five jobs (`ci`, `pack-check`, `release-scripts`, `repo-baseline`, `result`), each with `timeout-minutes: 15`; `ci`, `pack-check` and `repo-baseline` call `setup-dotnet`. `release.yml` has two jobs (`pack`, `publish`) that call it. Change the jobs that build or test in the workspace (`ci`, `pack-check`; `pack` in `release.yml`) to install both channels as a multi-line value (`10.0.x` and `11.0.x`), because the workspace `global.json` demands SDK 11.0.100 and the `net10.0` target and Nuke need the .NET 10 runtime. The `publish` job in `release.yml` runs after checkout, which brings in `global.json`, so it also needs an SDK that satisfies it if it calls `dotnet` in the workspace. Check what `publish.sh` and the NuGet steps need and install the same pair when `dotnet` runs from the workspace. The `repo-baseline` job runs `dotnet run tool/sync.cs` from a separate clone outside the workspace, so the workspace `global.json` does not apply to it; leave it at `10.0.x` unless the pinned repo-baseline release requires otherwise, and record the reasoning. Keep the pinned `actions/setup-dotnet` digest and its version comment. The `ci` job runs the whole suite for both frameworks on three MongoDB image legs; see the timeout criterion above. `release.yml` has no PR trigger and is not run in this task.

### Documentation

`README.md` ("Targets .NET 10.") and the `.NET` section of `docs/requirements.md` list .NET 10 and .NET 11. `docs/migrating-from-0.x.md` has the heading "Platform: .NET 10 only, lowered dependency minimums" and says the packages target `net10.0` only. Reword it so it stays accurate with `net11.0`: 0.x consumers must move off `net8.0` and `net9.0` to .NET 10 or later. `docs/compatibility-policy.md` states the general rule for dropping .NET versions and needs no change. `CHANGELOG.md` is generated at release time. The historical plans, including `0208`, are not edited. Root `AGENTS.md` is not edited. Its statement that tests target multiple frameworks is true again after this change.

### Publication and handoff

- PR title: a natural-language changelog entry such as the new .NET 11 support; the description contains the `Closes #209` line.
- The description names the SYSLIB0066 suppression and its reason, the Docker flake finding (reproduced or not, and what the pipeline now does), the verification evidence (build, `build.sh Test` totals per framework, coverage, pack contents), the C# 15 check result, the measured `build.sh Test` wall time with any `timeout-minutes` change, and the `CI after publication` jobs as pending until they run on the exact published head.

Operational follow-up, owned by the maintainer, not an acceptance criterion:

- Close the open Renovate PRs that raise the Microsoft.Extensions packages to 11.x, and decline further ones. The agent does not close forge PRs. State this in the description.
- The release workflow cannot run before merge. Its first real run is the next release, rc.2 or later, and checks that `pack` and `publish` work with both SDKs. A maintainer should watch that run. Its timing is not specified, so it stays an open handoff item.
