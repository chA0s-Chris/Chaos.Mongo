# Check migration lock ownership inside the migration transaction

> Issue: [#317](https://github.com/chA0s-Chris/Chaos.Mongo/issues/317)

## Rationale

`MongoMigrationRunner` checks the migration lock's lease on the client before every protected step (#312, #315), but the lock does not fence writes. A runner that stalls after its last check can lose an expired lock to another instance and still commit afterwards. Issue #317 asks for an ownership check that runs on the server, inside the migration transaction, so that it is atomic with the commit: the transaction writes to the lock document, filtered on the lock's `AcquisitionToken` and an unexpired `LeaseUntilUtc`, and MongoDB then decides between the contenders. A runner that lost the lock aborts and stops like any other lock loss; a takeover that starts after the write waits until the transaction ends.

Probing MongoDB 8.0 during planning showed two constraints the issue does not mention, and they decide the placement of the write. First, every write the lock document receives after a transaction's snapshot, including the runner's own lease renewals, makes a later transaction write to that document fail with `WriteConflict` (`TransientTransactionError`), and a filter on `LeaseUntilUtc` is evaluated against that older snapshot. A write placed right before the commit would therefore report a false lock loss whenever a renewal ran during the transaction. Second, a transaction that has written the lock document holds it until it ends, and a write from outside waits for that. The write is therefore the first operation of the transaction, which also makes the snapshot fresh. The renewal loop waits behind it, so the transaction has to end before the lease does; if the lease runs out first, the run stops as a lock loss once the client-side guards notice it, which rolls the transaction back as long as that happens before the commit is sent (the commit itself is outside what the runner can still cancel; see Technical Details, Compatibility). The owner accepted this change for transactional runs (see Technical Details, Owner decisions).

## Acceptance Criteria

- [ ] When a migration runs in a transaction, the runner writes to the lock document inside that transaction as the first server operation, before `ApplyAsync`, filtered on the lock's `Id`, `Holder`, `AcquisitionToken` and `LeaseUntilUtc` greater than the lock's `TimeProvider` now. The write changes the document, so it conflicts with a concurrent change and does not complete as a no-op.
- [ ] When that write matches no document, or fails with a `WriteConflict` carrying the `TransientTransactionError` label, the runner treats the lock as lost: it cancels `lockLostCts`, logs at Warning, aborts the transaction and throws an `OperationCanceledException` without applying the migration or recording history. The lock instance reports `IsValid == false` afterwards. Any other exception from the write propagates as a failed migration and is not mapped to lock loss. The runner never retries the migration.
- [ ] The write is serialized with the lock's own lease extension, so a renewal that is in flight when the transaction starts cannot turn into a spurious conflict. A renewal issued while the transaction is open waits for it and completes normally if the transaction ends before the lease does; a transaction that outlasts the lease remaining at its start, with the expiry detected before the commit is sent, ends as a lock loss (`OperationCanceledException`, rollback, no history entry) through the existing client-side guards. Expiry that only happens while the commit is already in flight is not promised to roll back: the commit then has the outcome MongoDB gives it, committed or not, and the takeover still cannot interleave with it.
- [ ] Runs without a transaction (`UseTransactionsForMigrationsIfAvailable` disabled, or a server without transaction support) and locks that do not support the check (custom `IMongoLock` implementations) behave as before: client-side checks only, no extra server operation.
- [ ] No public API changes: `IMongoLock`, `IMongoHelper` and the `PublicAPI.*.txt` files are untouched. The new lock document field is documented on `MongoLockDocument` and its persisted name is pinned by a test, as for the existing fields.
- [ ] Integration tests against the real server (in the `Integration` folder, with `[Category("Integration")]`) cover a takeover before the ownership write (case a): the stalled runner throws `OperationCanceledException` and neither commits the migration's transactional writes nor a history entry, and the taking-over runner applies the migration once.
- [ ] An integration test covers a takeover attempt between the ownership write and the commit, while the stalled runner still passes its client-side checks (case b, owner decision Q2): the test first observes on the server that the contender's eligible lock acquisition (its `findAndModify` on the lock collection) is active while the holder's transaction is still open, and only then releases the holder. While the transaction is open the contender does not acquire the lock; the stalled runner commits its writes and exactly one history entry; the contender then acquires the lock, sees that history entry and applies nothing, without failing. The test attributes the committed writes and the history entry to the first runner. The holder's lease renewal is suppressed during this race.
- [ ] Integration tests cover renewal versus transaction (owner decision Q1), each with positive evidence of the server interaction rather than elapsed time: (1) a transactional migration that stays open across a renewal whose real extension command is observed pending on the server while the transaction is open, with a lease that still has ample time remaining, completes with one history entry, the lock never reported lost, and a stored `LeaseUntilUtc` that has advanced after the commit; (2) a transactional migration whose ownership write and a session-bound data write have both succeeded, and which then outlasts the remaining lease while `ApplyAsync` is still running, i.e. before the commit is sent (driven by a controlled clock or an equivalent bounded wait), throws `OperationCanceledException`, commits none of its writes (the data write is absent afterwards) and records no history entry.
- [ ] Unit tests cover the runner's mapping with hand-written doubles: lost lock (no match), write conflict, other exception, no session, and a lock without fencing support, plus the lock's own behavior (serialization with extension, marked lost on a refusal, refused after disposal).
- [ ] The existing integration tests that edit the lock document or depend on renewal while a transaction is open are adapted without weakening what they assert, and the existing runner unit tests pass unchanged.
- [ ] `docs/migrations.md` states that only transactional runs get the server-side guarantee and that other runs keep the client-side checks, that effects outside the supplied session cannot be guarded, that the transaction holds the lock document so renewals and takeovers wait until it ends (so the lease remaining when a transaction starts must cover that transaction, with margin for the time already used by earlier steps of the run and for the commit; the configured lease and the server's transaction time limit are the sizing inputs), that expiry detected before the commit is sent rolls the transaction back while expiry during the commit leaves its outcome to the commit, and that in no case can a takeover interleave with the commit, and, for sharded clusters, the pre-provisioning requirement from Technical Details. `docs/distributed-locking.md` is updated where it describes the remaining overlap window. The `MongoOptions.MigrationLockLeaseTime` XML documentation no longer promises renewal during a transactional migration. `docs/compatibility-policy.md` records the new lock-document field and that older instances do not fence.
- [ ] `./cleanup_code.sh` has been run and its diff inspected, `dotnet build -c Release Chaos.Mongo.slnx` reports no warnings or errors, `./inspect_code.sh --base origin/main` reports no findings at warning or error severity, and `bash ./build.sh Test` passes with merged line coverage of at least 95%.

## Technical Details

- **Placement.** The write is the first server operation of the transaction, after `TryStartTransactionAsync` and the existing guard in `ApplyMigrationAsync`, before `migration.ApplyAsync`. `TryStartTransactionAsync` only starts the transaction on the client; the server transaction and its snapshot begin with this write, so the `LeaseUntilUtc` predicate is evaluated on current data. Placing it before the commit was rejected after probing MongoDB 8.0.38 in a scratch container: (1) a renewal committed after the snapshot makes the transaction's write fail with `WriteConflict`; (2) the predicate sees the older lease value; (3) an update that changes nothing never conflicts, so a "touch" with an unchanged value would not fence at all; (4) an outside write that matches waits until the transaction ends, while a non-matching takeover attempt (unexpired lease) returns at once with a duplicate-key result that `TryAcquireLockAsync` already maps to `null`. Holding the document from the start costs only the delay the issue already accepts: an expired lock cannot be taken over while the holder's transaction is open. The consequence for renewals is spelled out in the Rationale and must reach the docs. With the default 10-minute lease and MongoDB's default 60 s transaction limit it is normally not visible; it matters when the lease remaining at the start of a transaction is shorter than that transaction (see Compatibility).
- **What to write.** A dedicated `Int64` field on `MongoLockDocument`, incremented with `$inc`. Extending `LeaseUntilUtc` inside the transaction was rejected: it would need `MongoLock.ValidUntilUtc` to advance only after a successful commit and stay unchanged on abort, and renewals are blocked during the transaction anyway. The field name follows the repository's persisted-name pinning (see `MongoLockDocumentTests`); documents without it stay valid and older library versions ignore it through `[BsonIgnoreExtraElements]`. A takeover leaves it alone.
- **API.** Internal first, as the issue allows. A new internal interface (new component, for example `ITransactionFencedLock : IMongoLock`) with a method that takes the `IClientSessionHandle` and a cancellation token; `MongoLock` implements it and the runner uses it only when `mongoLock is` that interface and a session exists. `MongoHelper` supplies the server operation to `MongoLock` the way it supplies the extension, as a new internal method next to `ExtendLockAsync` and a new optional delegate on the internal `MongoLock` constructor, so existing constructor calls and `MongoLockTests` keep compiling. A public `IMongoLock.EnsureHeldAsync` member can follow once this has proven itself; it would be a breaking change for implementers of the interface and is not part of this issue.
- **Lock behavior.** The method takes the existing `_operationSemaphore`, the one that serializes `TryExtendAsync` and `DisposeAsync`, only for the duration of the write. It returns "not held" without a server call when the lock is already lost or disposed, and marks the lock lost when the write matches nothing, as a refused extension does. A `WriteConflict` is reported to the runner as lost as well. The filter uses the lock's own `TimeProvider`, as extension does, and adds no new clock assumption.
- **Error mapping.** Map only `WriteConflict` with the `TransientTransactionError` label (`MongoCommandException` or `MongoWriteException`, code 112). Other transient errors, such as a primary step-down, are not proof of a lost lock and fail the migration as today. `ApplyMigrationAsync` drives the transaction by hand, so nothing retries it. The new check reuses the existing lock-loss path (`SignalLockLostAsync`, Warning log, `OperationCanceledException` carrying the protected token), so the catch block, the transaction abort and the final Warning stay as they are. After the server aborted the transaction on the conflict, the existing `AbortTransactionIfActiveAsync` already swallows the failing abort.
- **Not part of the guarantee.** The existing client-side guards stay: they are the only protection outside a transaction and they stop a runner whose lease has already expired. Effects outside the supplied session, anchoring and sealing are unchanged, as the issue states. Note for the tests and the PR: in transactional runs the history entry's `_id` (the migration id) already makes a second concurrent commit of the same migration fail with `WriteConflict` (probed: two transactions inserting the same `_id`, in either order, with or without an older snapshot). The ownership write does not add exactly-once for the history; it adds a deterministic winner, orders the contenders instead of failing the later one with a driver error, and reports the loser as a lock loss.
- **Test seams.** `Chaos.Mongo.Tests` has `InternalsVisibleTo`, so a test can construct `MongoMigrationRunner` directly with a decorating `IMongoHelper` that returns a decorating lock implementing the internal interface and delegating to the real `MongoLock`. The decorator can delay before or after the ownership write and can pin `IsValid`, which stands in for a runner stalled after its last client-side check. Use hand-written doubles for the unit tests, not Moq (`tests/AGENTS.md`). The server operations belong in integration tests because MongoDB semantics are the subject. Gate and bound every task with the repository's usual timeouts, and attribute writes to the intended winner (for example a field carrying the holder id) so that the unique history `_id` alone cannot satisfy an assertion.
- **Forcing the takeovers.** Case (a) happens before the ownership write, so no server transaction exists yet: the test writes a past `LeaseUntilUtc` into the lock document and acquires the lock through a second helper with another holder id. Case (b) must not write to the lock document, because that write would wait for the open transaction while the decorator waits for the write (deadlock), and a write released only after the commit would not test the contested acquisition. Instead the second helper uses its own controlled `TimeProvider` (a `FakeTimeProvider` advanced past the holder's lease) so that its acquisition predicate judges the stored lease expired. The test starts that acquisition after the ownership write without awaiting it, gives the contender's client a unique `appName`, and polls `$currentOp` (aggregate on the `admin` database; the fixture has no authentication) with a bounded wait until an active operation with that `appName`, a `findAndModify` command and the lock collection's namespace is listed. That is the positive evidence that the eligible acquisition reached the server while the holder's transaction was open; a started task, a pending `Task` or an unchanged lock document are not sufficient on their own, because they also hold while the contender is still in server selection or connection checkout. Only then does the test assert that the acquisition is still pending and the holder's lock document unchanged, release the holder, and await both tasks within a bound. Match only on those stable fields: the fixture runs on every image of the CI matrix (`MinimumSupported`, `Primary`, `Latest`), and lock-wait diagnostic fields of `$currentOp` differ between versions and must not be asserted. The holder's clock stays independent of the contender's, and the holder's renewal is suppressed for this test (the decorator refuses to issue it, or the lease is long enough that no tick falls into the race).
- **Renewal tests.** A decorator seeing the renewal call enter `TryExtendAsync` does not prove that the extension command reached MongoDB, and one history entry plus a valid lock would also pass for an implementation that suppressed the renewal or ran it only after the commit. For Q1 test (1), keep the holder's transaction open (gated) until `$currentOp` (same polling as in "Forcing the takeovers", with a `findAndModify` on the lock collection from the holder's own `appName`) shows the renewal pending on the server, then release the transaction while the lease still has ample time remaining (use a lease of several seconds, or a controlled clock, so that scheduling cannot flake it). After the commit, assert that the renewal succeeded: the stored `LeaseUntilUtc` is later than before the transaction and the lock was never reported lost. For test (2), first observe that the ownership write and a data write through the migration's session have succeeded (the migration signals this from inside `ApplyAsync`), only then advance the holder's clock past the lease (or wait it out with a bound) while the migration is still inside `ApplyAsync`, and assert the lock-loss `OperationCanceledException`, that the data write is not visible afterwards and that no history entry exists. The existing in-progress lock-loss test writes its data before its blocked await, so it does not replace this rollback assertion; the refused-renewal cancellation path is kept by the unit tests of the runner and by case (a) with the custom-lock fallback. This is also where to confirm that lease exhaustion behind the blocked renewal surfaces as the lock-loss `OperationCanceledException` of the run: `TryExtendLeaseAsync` cancels the blocked extension at the lease's expiry, and `RunLeaseRenewalLoopAsync` currently logs that cancellation at Error ("failed unexpectedly") before signalling the loss. Keep that existing logging unless test (2) shows the run ending any other way; the run's own Warning remains the lock-loss record, and no change to the renewal loop is planned for the log level.
- **Existing tests.** Two existing tests are affected: `RunMigrationsAsync_WithLockStolenWhileTransactionalMigrationInProgress_AbortsTransactionAndDoesNotRecordMigration` edits the lock document while the transaction holds it, so the edit would wait until the transaction ends; `RunMigrationsAsync_WithMigrationLongerThanLease_RenewsLeaseAndCompletes` relies on renewal during a migration that outlasts its lease and has to run without a transaction to keep covering the renewal loop. Both keep their assertions, except that the first must state in its name or a comment what it now proves (a stolen holder is still detected, but through the client-side guards or the ownership write, not through a renewal that waits behind the transaction); the Q1 tests above are the transactional counterparts.
- **Owner decisions** (recorded after plan readiness round 1 from the owner's reply in the KanDev chat). *Q1, renewal during a transactional migration: accept.* A transactional migration no longer renews its lease while its transaction is open, because the renewal waits behind the ownership write on the same lock document; a transaction that outlasts the lease remaining at its start ends as a lock loss, with a rollback if the expiry is detected before the commit is sent. This reverses the documented renewal contract for transactional runs only (`MongoOptions.MigrationLockLeaseTime` XML docs, `docs/migrations.md`), so it needs the documentation, operator guidance (the lease remaining at the start of each transaction must cover it, see Compatibility) and the Q1 integration tests from the Acceptance Criteria. Preserving renewal during the transaction is out of scope. *Q2, second race: the holder commits.* A contender that attempts takeover after the ownership write waits until the transaction ends; the holder still passes its guard and commits, and the contender then applies nothing. A holder abort triggered by a waiting contender is not part of the design.
- **Sharded clusters.** The lock document can live on a different shard from a migration's data or its history collection, and MongoDB does not allow creating a collection inside a transaction that spans shards. A transactional migration that so far touched only one shard (and relied on implicit creation of a collection there) can therefore start failing once the ownership write adds a second shard. State this in `docs/migrations.md` and the PR description: on a sharded cluster, pre-create the collections a migration writes (including the history collection) or disable `UseTransactionsForMigrationsIfAvailable`. The compatibility claim below is conditional on that; the replica-set integration fixture cannot establish sharded behavior, and the plan makes no claim that it was tested.
- **Compatibility.** Persisted data and the public API stay compatible; rolling upgrades are safe because older instances ignore the new field and simply do not fence (`docs/compatibility-policy.md` gets the note next to the lock document's token bullet). Behavior changes for transactional runs in two cases: a transaction that outlasts the lease, and a sharded deployment as described above. The first depends on the lease remaining when the transaction starts, not on the configured lease alone: one lease and one renewal loop span the history read and the whole batch, renewal is scheduled at half the remaining lease, and a later migration can start partway through the lease (for example a transaction needing 8 s under a configured 10 s lease can start with 6 s left). The rollback guarantee covers expiry detected before the commit is sent. The commit is the one step the runner cannot revoke: the last guard (`MongoMigrationRunner.cs`, after the history insert) checks local validity and then sends `CommitTransactionAsync`, and the lease can still run out after that check, even after the server has committed but before the reply arrives. In that interval the ownership write still orders any takeover after the transaction, so the migration is not applied twice, but cancellation of the awaiting call does not prove a rollback and the plan and docs must not claim one; the margin for commit latency is what keeps this interval unlikely. Deployments whose transactions are short compared with the configured lease will not notice the behavior change; the configured lease and the server's `transactionLifetimeLimitSeconds` (default 60 s, which a deployment may raise) are the sizing inputs, and the documentation says to leave margin for the time already used and for the commit.
