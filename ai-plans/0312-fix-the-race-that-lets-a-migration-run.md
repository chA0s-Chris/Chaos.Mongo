# Fix the race that lets a migration run after its lock lease has expired

> Issue: [#312](https://github.com/chA0s-Chris/Chaos.Mongo/issues/312)

## Rationale

`MongoMigrationRunner` must not read the migration history, apply a migration, or record one once it knows that its lock lease has expired. `EnsureLockStillValidAsync` detects the invalid lease, but then relies on the linked `protectedCts` already being cancelled. When the renewal loop has cancelled `lockLostCts` with `CancelAsync`, that propagation runs later on the thread pool, so the guard can pass and a migration can run under a lock the runner knows it has lost. CI hits this intermittently in `RunMigrationsAsync_WithAlreadyExpiredAcquiredLock_StopsBeforeReadingHistoryOrApplyingAnyMigration`.

The guard must also treat a cancelled `lockLostCts` as a lost lock: the renewal loop cancels it on any unexpected extension failure, even while the lease is still locally valid, and today the guard lets that case through.

The goal is a guard that stops the run deterministically, regardless of thread-pool timing, and certainty that no other code in `src/` depends on the same propagation.

## Acceptance Criteria

- [ ] When `EnsureLockStillValidAsync` finds the migration lock invalid, `RunMigrationsAsync` throws an `OperationCanceledException`. From that point on it reads no history and applies or records no migration, whether or not the cancellation has reached `protectedCts` yet.
- [ ] When `lockLostCts` is already cancelled, for example after a lease extension threw while the lease was still locally valid, `EnsureLockStillValidAsync` also throws an `OperationCanceledException`, even though `IsValid` still reports `true` and `protectedCts` may not be cancelled yet.
- [ ] New tests call `EnsureLockStillValidAsync` directly with a separate, uncancelled protected token and cover: (a) an invalid lock with a cancelled `lockLostCts`; (b) a valid lock with a cancelled `lockLostCts`; (c) an invalid lock with an uncancelled `lockLostCts`, after which `lockLostCts` is cancelled; (d) an invalid lock with an uncancelled `lockLostCts` and a callback that throws, registered on a token linked to `lockLostCts` as a migration's token is, where the guard still throws an `OperationCanceledException` and logs a separate warning that carries the callback's exception. Cases (a) and (b) fail against the original `EnsureLockStillValidAsync` logic (reverted locally, not committed) and pass with the fix, and the PR description reports the observed failures.
- [ ] Runner-level tests show that `RunMigrationsAsync` (a) queries no history when the acquired lease is already expired, by strengthening the existing already-expired-lock test through `FakeHistoryCollection`'s `onFind` hook; (b) inserts no history entry when a migration ignores its token and `ApplyAsync` returns normally after the lease expired; and (c) throws an `OperationCanceledException` without applying the pending migration (`ApplyCallCount` stays 0) when the history read returns normally after the fake clock has passed the lease expiry.
- [ ] All other existing `MongoMigrationRunnerTests` pass unchanged.
- [ ] The PR description lists every `CancelAsync()` call site in `src/`, including the runner's own, and for each names what keeps dependent code safe even when cancellation is already in progress, for example serialized callers, a check of the cancelled source's own state, or a join with the task that owns the work. A confirmed gap is changed so its check reads the cancelled source's own state, awaits the propagation, or joins the owning task, and gets a regression test for that caller.
- [ ] `./cleanup_code.sh` has been run and its diff inspected, `dotnet build -c Release Chaos.Mongo.slnx` reports no warnings or errors, `./inspect_code.sh --base origin/main` reports no findings at warning or error severity, and `bash ./build.sh Test` passes with merged line coverage of at least 95%.

## Technical Details

- Fix: `EnsureLockStillValidAsync` returns only when the lock is valid and `lockLostCts` is not cancelled. Otherwise it cancels `lockLostCts` with `CancelAsync` if that has not happened yet, to signal work a migration may have left running, and throws `new OperationCanceledException(<lock lost>, protectedCancellationToken)` unconditionally. `CancelAsync` stays, so cancellation callbacks such as a migration's own continuations never run inline on the renewal loop or the guard. The guard's warning distinguishes an expired lease from a loss the renewal loop signalled, and the guard's XML remarks and the `protectedCts` comment in `RunMigrationsAsync` are updated to the new rule.
- A callback that runs during the cancellation of `lockLostCts` can throw and fault the awaited `CancelAsync`. This includes a migration's own registration on its token, which runs through the propagation to the linked `protectedCts`. The guard catches that fault, logs it as a separate warning, and still throws the `OperationCanceledException`.
- Exception behavior: both the old and the new guard throw with the linked token. A cancellation raised by the guard takes precedence over a concurrent renewal fault, including when the lease still reports valid, because `RunMigrationsAsync` rethrows the protected-work exception before the renewal exception; the renewal loop still logs its fault. When no protected-work exception takes precedence, the renewal fault is rethrown as before. Otherwise only the message differs.
- Test seam: `EnsureLockStillValidAsync` becomes `internal` (`Chaos.Mongo.Tests` already has `InternalsVisibleTo`). A separate, uncancelled token stands in for a `protectedCts` whose propagation is still pending, so the tests need no thread-pool control and no `[NonParallelizable]`. A sociable test through `RunMigrationsAsync` cannot delay the propagation from `lockLostCts` to `protectedCts` without starving the thread pool, so this is the solitary exception `tests/AGENTS.md` allows. The tests use the file's hand-written doubles, not Moq.
- Audit result during planning: `AnchorCompletionNotifier`, `MongoQueueSubscription`, `OutboxProcessor`, `EventStreamSealingSweep` and `IntegrityAnchoringService` either await `CancelAsync` before a dependent check or check the cancelled source itself. The runner's own `renewalStopCts.CancelAsync()` is safe because the renewal loop awaits and filters on `stopToken` itself. `AnchoringRun`, `EventStreamSealingSweep.EnsureLockAsync` and `MongoLockExtensions.EnsureValid` are other lease guards, not `CancelAsync` sites; they act on `IsValid` directly. The audit did not yet consider cancellation already in progress: a second, concurrent `CancelAsync()` can return while the first is still running the callbacks. `OutboxProcessor.StopAsync` called twice concurrently is a case to check, because a cancellation callback arms the finalization grace period. The implementation completes the audit on this basis for the PR description.
- No public API or documented contract changes: `RunMigrationsAsync` still throws `OperationCanceledException` when the lease is lost.
